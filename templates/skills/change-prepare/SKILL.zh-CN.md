# 准备变更

项目上下文如果指定了 OpenSpec CLI 的调用方式，请在执行原生步骤和下列命令时使用它。

1. 阅读一次[项目上下文](references/project.md)，然后打开所选的原生入口。新变更使用 OpenSpec 的准备入口，进行中的变更使用修订入口。先满足入口的前置条件并加载其上下文，再开始调查。缺少必需的入口或工作流根目录时，停止准备并报告。
2. 在原生检查步骤，一起读取可能涉及的实现、最接近的测试以及适用的规则段落。对于共享类型、校验器或辅助函数，先搜索其引用，并检查所请求范围之外的使用方，再确定变更边界。在各份产出物中复用这些发现。继续阅读时，应有具体的范围、规则或验收问题需要解决。
3. 使用项目上下文中的**现有检查**，记录最接近的测试和适用的 lint 或类型检查的命令与工作目录。需要补足细节或验证触发条件时，再打开包清单和钩子来源。行为变更在获批前，须把明确的拒绝场景和保留行为场景写入原生规格。使用原生场景标题，将预期行为与相应任务关联。
4. 在规划预算内按依赖顺序写入原生产出物。合并相互独立的读取，每次写入后检查所要求的原生状态。保留原生工作流要求的依赖重读步骤。向开发者交接每份产出物前，完成适用的原生审阅，检查范围、验收、任务和验证有无遗漏。先处理可以解决的问题，再提交仍需人工批准的决定。
5. 使用[固定 GOAL 模板](references/GOAL.md)，在原生变更产出物旁为该变更创建 `GOAL.md`。保留原生文件布局，包括拆分后的每一份 Spec 和 Plan。填写当前变更的实际路径、原生实施入口、实际实施批准状态、检查和工作目录，以及可观察的完成标准与证据。
   - 在 **Reviewed write scope** 中逐项列出交付会改动的仓库相对路径及其允许用途，包括业务变更、适用的原生任务勾选项或状态，以及确有计划的证据或记录文件。根据该工作流的实际路径，将此清单与原生任务和所有证据写入位置逐一核对。仅在拟写入 GOAL 的记录内容已有明确定义且将接受明确审阅时，把 GOAL 本身列入。交付方编辑计划产出物也需要单独列入已审阅的写入范围。
   - 实施批准保持待定，直到人工明示批准覆盖当前已审阅的变更、修订版本和完整写入范围。按新 GOAL 的位置重写模板链接，确保指向仓库内部。链接已安装的[交付技能](../change-deliver/SKILL.md)和本项目的上下文。`/goal` 和兼容交付使用同一批产出物。填写全部占位项，命令、批准及 MR 平台均须有实际依据。
6. 在同一次修订中，将开发者反馈同步到 Spec、实施与验证任务，以及 GOAL。重新审阅改动的产出物并刷新原生状态。前置条件由原生状态和指令决定。OpenSpec 请运行 `openspec status --change <id> --json` 和 `openspec instructions apply --change <id> --json`。若 `isPlanningComplete` 为 false、`missingPrerequisites` 非空，或原生 apply 状态受阻，请补齐必需的产出物或明确报告待决定的问题。原生工作流要求的 `design.md` 仍是必需项。其他工作流也保留已安装的前置条件和人工批准要求。
7. 交接准确的变更 ID、当前 Spec 和 Plan 的链接、GOAL 路径、审阅结果、范围、检查、批准状态与未决事项。使用 [change-ready](../change-ready/SKILL.md) 进行只读的实施就绪检查。前置条件和必需批准全部落实后，才可报告就绪。

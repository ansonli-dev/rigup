# Prepare a change

1. Read [project context](references/project.md) once and open the selected native entry. Use OpenSpec's preparation entry for a new change or its revision entry for an active change. Follow the entry's prerequisites and load its context before discovery. Stop at a missing required entry or workflow root.
2. At the native inspection step, batch the likely implementation, its nearest test, and applicable rule sections. For a shared type, validator or helper, search its references and check consumers outside the requested scope before choosing the boundary. Reuse these findings across artifacts. Read further only to resolve a specific scope, rule or acceptance question.
3. Use **Existing checks** in the project context to record the command and working directory for the nearest test and applicable lint or type checks. Open package and hook sources for missing details or to verify claimed trigger coverage. For a behavior change, put concrete rejection and preservation cases in the native spec before approval. Use the native scenario titles to connect the expected behavior to the relevant tasks.
4. Write the native artifacts in dependency order within the planning budget. Group independent reads and pair each write with the required native status check. Preserve native dependency rereads. Before handing each artifact to the developer, run the applicable native review and check any uncovered scope, acceptance, task and verification gaps. Fix resolvable findings first; report unresolved decisions for human approval.
5. Create a change-scoped `GOAL.md` from the [fixed GOAL template](references/GOAL.md) beside the native change artifacts. Keep the native layout, including every split Spec and Plan file. Fill all fields with this change's actual paths, native implementation entry, actual implementation approval status, checks and working directories, observable completion criteria and evidence.
   - Enumerate every repository-relative file delivery will modify in the **reviewed write scope**, with its permitted purpose: business changes, applicable native task checkboxes/status, and actually planned evidence or record files. Reconcile this list with the native tasks and every evidence destination. Use the selected workflow's actual destinations. Include the GOAL itself only for a defined record write that will be explicitly reviewed; creating or reading a planning artifact does not authorize delivery to edit it.
   - Preparation approval does not imply implementation approval; keep implementation approval pending until explicit human approval covers the current reviewed change, revision and full reviewed write scope. Rewrite template links relative to the new GOAL location so they resolve inside the repository. Link the installed [delivery skill](../change-deliver/SKILL.md) and this project's context; both `/goal` and compatibility delivery must consume these same artifacts. Do not leave placeholders or invent commands, approvals, or an MR platform.
6. Propagate developer feedback across the Spec, implementation and verification tasks, and GOAL in one coordinated revision. Re-review changed artifacts and refresh native state. Native status and instructions determine prerequisites: for OpenSpec run `openspec status --change <id> --json` and `openspec instructions apply --change <id> --json`. If `isPlanningComplete` is false, `missingPrerequisites` is nonempty, or the native apply state is blocked, complete the required artifact or report it as an open decision. Calling a native-required `design.md` optional does not waive it. Other workflows keep their installed prerequisites and human gates.
7. Hand off the exact change ID, current Spec and Plan links, GOAL path, review results, scope, checks, approval status and open decisions. Use [change-ready](../change-ready/SKILL.md) for the read-only implementation readiness check; do not claim readiness while prerequisites or required approvals remain open.

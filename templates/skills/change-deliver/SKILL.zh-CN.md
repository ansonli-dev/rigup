# 交付变更

开始编辑仓库前，先判断是否具备交付条件。缺少必需产出物或批准时，交接受阻，列出具体缺少的文件或决定，以及所需的准备步骤。紧急请求可以传达授权，未完成的原生规划仍须补齐。加载此入口后，遇到阻塞须按工作流处理。

项目上下文如果指定了 OpenSpec CLI 的调用方式，请在执行原生步骤和下列命令时使用它。

1. 在考虑实施批准前，完成下列只读写入范围检查。打开该变更的 `GOAL.md`、[项目上下文](references/project.md)和已安装的原生交付入口。`/goal` 和此兼容入口使用同一批已审阅的 GOAL、Spec 与 Plan，包括拆分后的每一份产出物。在仓库内解析引用，核实变更 ID、范围及修订版本均属当前同一变更。没有收到 GOAL 时，和原生变更产出物一起查找。必须使用当前变更的 GOAL。
   - 对于 OpenSpec，从项目根目录运行 `openspec list --json`，选择准确的活跃变更 ID。运行 `openspec status --change <id> --json` 和 `openspec instructions apply --change <id> --json`。核实 apply 所需的产出物已经完成，遵循原生 apply 状态，并检查范围内的任务。
   - 从 GOAL 完成标准、证据写入位置以及原生任务和 apply 指令中推导计划写入。在检查回复中逐项列出仓库相对路径与预期用途，包括业务变更、任务勾选项或状态，以及验证和证据记录。先按完成工作实际需要独立列出完整清单，再核对现有授权和已审阅范围。即使必需任务或证据文件未列在已审阅范围中，也要列入检查清单。检查期间只在回复中列出清单，保留仓库原样。
   - 将每项计划写入与 **Reviewed write scope** 逐项核对路径和用途。每个文件及其允许用途都须明确列出。有一项遗漏就阻止交付，包括编辑、更新任务勾选项及写入验证记录，即使当前请求明确授权该路径。报告遗漏的仓库相对路径与用途，交回 change-prepare 重新审阅范围并取得批准。范围补审前保持阻塞，暂缓实施批准检查和实施。
   - GOAL 本身只有在明确审阅某项具体记录写入后才可写入。旧版 GOAL 具有完整、等效的范围和证据即可接受，允许沿用原有格式。其他原生或客户工作流使用列出的交付入口，从实际任务与证据要求推导清单。检查剩余预算。
   - OpenSpec 的 `isPlanningComplete: false`、非空的 `missingPrerequisites`、未完成的必需产出物或受阻的 apply 状态都是阻塞项。即使负责准备的智能体把 `design.md` 称为可选，原生要求仍适用。即使 apply 响应的 `state` 是 `ready`，上述阻塞项仍然优先。须同时检查状态与前置条件。先通过准备步骤解决阻塞并刷新原生状态，再编辑仓库文件。
2. 写入范围检查通过后，核实实施批准以及其他原生或客户批准条件。批准须来自当前人工指令，或适用且经过验证的项目指定记录，明确批准同一变更 ID、范围和当前已审阅的修订版本。若当前人工指令明确更新同一修订版本和范围的批准状态，以新指令为准。批准缺失、待定、过期或范围不符时，交付受阻。开发者随后提交就绪检查生成的准确 `/goal` 命令时，才会启动已经获批的范围。在此之前，缺少的批准和其他原生前置条件都须补齐。范围有变化时交回审阅与批准。
   - 批准必须覆盖完整的已审阅写入范围。任何遗漏、指向其他修订版本或授权范围不同都将阻止交付。若完整当前范围已获明确批准，额外授权的路径与操作可同时存在。列出未使用的额外授权，交付仅使用已审阅的范围，计划却遗漏的路径仍须补审。需要改变范围时回到准备、审阅和批准。批准覆盖范围有歧义时，由批准者确认。当前的人工作出批准后，可按该批准处理早先记录为待定的状态，保留 GOAL 和批准记录原样。
   - 无法核实变更、必需产出物或批准时，保持仓库文件原样。报告缺少的前置条件，将请求交回 change-prepare 或批准者。即使请求立即实施，也须先补齐前置条件。
3. 阅读适用于拟更改文件的原始指南与项目开发规则。编辑请求类型、校验器或可复用辅助函数前，搜索其引用，检查获批范围之外的使用方是否仍保持预期行为。若已获批的方案会改变这些使用方，请在编辑前把相关任务交回修订和批准。沿用最近的实现和现有测试，在需要时扩展测试。使用当前钩子与 CI 检查。发现检查缺口时，说明缺少哪项检查以及适合放置的位置，供单独审阅。
4. 实施时遵循获准的 apply 步骤。审阅时检查当前 diff 和证据。改变行为时，按已批准的场景分别验证所请求的行为和应保留的行为。条件允许时，在实施前或一次性基线中观察新增回归测试按预期失败。交付前重跑行为检查和任务适用的项目命令，包括 lint 和类型检查。记录每条命令和结果。在任务范围与预算内处理失败条件，同一条件最多修复两次。
5. **每次推送**前，包括后续修复或证据提交，按已批准的范围检查完整待推送提交范围和 diff。审阅行为、共享使用方及验证结果。修复确认的问题，重跑受影响的测试，并在推送前再次审阅更新后的提交。记录范围、发现和实际检查结果。只有此 GOAL 及当前指令均授权时才能推送。
6. GOAL 如果包含 MR 跟进，先确认平台、项目和 MR 标识，只使用已配置的客户命令、原生 MCP 或已记录在项目文档中的 CLI。使用现有 CI、审阅者和合并配置。读取当前 MR head SHA、全部必需检查、已配置的 AI 审阅完成状态及全部讨论。每项必需检查都必须在该 SHA 上通过，已配置的 AI 审阅须明确完成，每条发现都要有处理记录。即使讨论为空，也要确认审阅已完成，通过结果必须对应最新 SHA。
   - 在本地修复已确认且在范围内的问题，添加或更新回归检查，重跑受影响的测试，审阅待推送提交，推送后继续跟进新的 SHA。为有争议的发现记录证据，把扩展的范围交回审阅。缺少访问权限、结果仍在等待或预算用尽时，保留待办状态。
   - 结束前重新读取 MR head。若检查期间 head 有变化，对新 head 重新检查、审阅并记录各项处理结果。即便只推送证据提交，也要收集当前 head 的新证据。
7. 仅更新已审阅范围内的任务状态及证据位置，只记录已验证的工作，并逐项记录 GOAL 完成标准的结果。若需要增加写入位置，先回到准备和范围批准。满足前置条件并获得授权后，遵循原生验证和收尾步骤。交接变更 ID、GOAL、diff、检查结果，以及范围内的当前 MR SHA 与证据，并列出尚未执行的检查或阻塞项。仍有失败时，附上证据、已尝试的修复与下一责任方。

这些指令为加载技能的智能体提供操作指引。宿主权限负责控制文件系统访问。技能本身无法在运行时验证写入范围或保证遵守流程。无论请求的紧急程度，加载此技能后仍须满足所有前置条件。

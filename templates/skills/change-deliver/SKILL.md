# Deliver a change

The entry decision comes before any source or test edit: if a required artifact or approval is missing, return a blocked handoff naming that file or decision and the preparation step needed. An urgent request can authorize work; it cannot make incomplete native planning complete. Do not switch to direct-edit mode after loading this entry to evade a blocker.

1. Check delivery prerequisites before editing. Open the change-scoped `GOAL.md`, [project context](references/project.md) and the installed native delivery entry. Both `/goal` and this compatibility entry use the same reviewed GOAL, Spec and Plan, including every split artifact. Resolve references within the repository and verify the same current change ID, scope and revision. If no GOAL is supplied, locate it with the native change artifacts; do not silently substitute an older or different change.
   - For OpenSpec, run `openspec list --json` from the project root and select the exact active change ID. Run `openspec status --change <id> --json` and `openspec instructions apply --change <id> --json`. Verify the artifacts required for apply are done, honor the native apply state, and inspect the scoped tasks.
   - Verify human approval for the same change ID and scope, from the current conversation or the project's designated approval record. Explicit submission of the ready-produced `/goal` with this exact reviewed GOAL authorizes implementation of that same scope. A generic start request or urgency does not establish missing approval. Extra native prerequisites and approvals still apply; changed scope must return for review.
   - OpenSpec's `isPlanningComplete: false`, nonempty `missingPrerequisites`, unfinished required artifacts or blocked apply state remain blockers, even if a preparation agent called `design.md` optional. These blockers take precedence over an apply response whose `state` is `ready`: check both status and prerequisites, not the state label alone. Do not write source or tests until the blockers are resolved through preparation and native state is refreshed.
   - For other native or customer workflows, use the listed delivery entry and verify its required artifacts and approvals. Check the remaining budget.
   - If the change, required artifacts, or approval cannot be verified, stop before editing source or tests. Report the missing prerequisite and route the request to change-prepare or the approver. The prerequisite remains in effect even when the request asks for immediate implementation.
2. Read the original guidance and project development rules that apply to the files you will change. Before editing a request type, validator, or reusable helper, search its references and verify that consumers outside the approved scope keep their behavior. If the approved approach would change those consumers, return the affected task for revision and approval before editing. Follow the nearest implementation and reuse or extend its existing test. Use the current hooks and CI checks. When they leave a gap, describe the missing check and where it belongs so it can be reviewed separately.
3. For implementation, follow the authorized apply steps. For review, inspect the current diff and check evidence. For behavior work, check the approved cases and exercise the requested behavior and the preservation case. When possible, observe the new regression test fail for the expected reason before the implementation or in a disposable baseline. On the delivered change, rerun the behavior check and run the applicable project commands from the task, including lint and type checks. Record each command and result. Address a failing condition within the task and budget, with at most two repair attempts for that condition.
4. Before **every push**, including a follow-up fix or evidence commit, inspect the complete outgoing commit range and diff against approved scope. Review behavior, shared consumers and verification; fix confirmed findings, rerun affected checks and review the revised commits before pushing. Record the range, findings and actual check results. Push only when authorized by this GOAL and the current instructions.
5. If GOAL includes MR follow-up, confirm the platform, project and MR identity, then use only its configured customer commands, native MCP or documented CLI. Consume existing CI, reviewer and merge configuration; do not create a pipeline, reviewer or policy. Read current MR head SHA, all required checks, configured AI review completion and all discussions. Every required check must pass for that SHA; a configured AI reviewer must explicitly finish and every finding must have a recorded outcome. Pending review with empty discussions and older green SHAs are incomplete.
   - Fix confirmed in-scope findings locally, add or update regression checks, rerun affected tests, review outgoing commits, push and follow the new SHA again. Record evidence for disputed findings; return expanded scope for review. Missing access, pending results or exhausted budget remain open work.
   - Re-read the MR head before completion. If it changed during inspection, repeat the check/review/disposition loop for the new head. Any evidence-only commit that is pushed also needs fresh current-head evidence.
6. Update task status only for verified work and record results against every GOAL completion criterion. Follow native verification and closure steps when their prerequisites and authorization are satisfied. Hand off the change ID, GOAL, diff, check results, current MR SHA/evidence when in scope, and any unrun checks or blockers. For an unresolved failure include the evidence, attempted fixes and next owner.

These instructions guide an agent that loads the skill; they cannot prevent writes when a host or agent bypasses it. Host permissions enforce filesystem access. Once loaded, workflow prerequisites remain in force even when the request asks for immediate edits.

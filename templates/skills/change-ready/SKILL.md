# Check implementation readiness

This is a read-only review. Do not edit artifacts, source, tests, task status, configuration or approval records. Do not install dependencies or run mutating checks. Stay within the review budget.

1. Read [project context](references/project.md), the change-scoped `GOAL.md`, and the selected native workflow entries. Identify the exact change ID, revision and reviewed write scope. Resolve every GOAL, Spec and Plan reference, including split artifacts, relative to its containing file. Verify each file exists within the repository, belongs to this same current change and reflects the latest revision; a plausible link to another change is a blocker. Check applicable original guidance and each installed entry's prerequisites.
   - Reconcile all planned writes with the reviewed write scope: business files, applicable native task checkboxes/status, and evidence/record destinations. Each file delivery will modify must be explicitly covered with its permitted purpose. The GOAL itself is writable only if explicitly reviewed for a defined record write. Accept older GOALs with complete equivalent scope and evidence regardless of formatting; a new heading or table is not required. If a planned write is missing, name its repository-relative path (including an expected task-file update), block readiness and return to change-prepare for scope review and approval.
2. Read native readiness evidence. For OpenSpec run `openspec list --json`, `openspec status --change <id> --json` and `openspec instructions apply --change <id> --json` from the project root. Native status and instructions are authoritative: `isPlanningComplete: false`, nonempty `missingPrerequisites`, a blocked apply state, or unfinished required artifacts withhold readiness. A preparation agent calling `design.md` optional cannot waive a native requirement. Other workflows use their installed prerequisite commands and human approval gates. Verify all required approvals, including explicit human approval for implementation of this current reviewed change, revision and scope, from the current human instruction or an applicable, verified project-designated approval record. A current human instruction explicitly updating approval status supersedes an older status for that same revision and scope. Missing, pending, stale or scope-mismatched implementation approval blocks readiness even when native planning is complete. Resolve conflicting approval evidence with the approver; do not create approval through this check.
   - Approval must cover the full reviewed write scope. An approval that omits any part, names another revision, or authorizes a different scope blocks readiness. Genuine additional authorization can coexist with explicit approval of this entire current reviewed scope; identify the extra paths/actions as unused and keep them outside delivery. It neither reviews those extras nor repairs an omitted planned path. A requested or necessary scope change returns to preparation, review and approval; ambiguous coverage goes to the approver. A current approval can supersede an older pending record without editing the GOAL or writing an approval record.
3. Map every material acceptance criterion to a concrete native implementation task and verification method. Include rejection and preservation scenarios. Verify commands and working directories against project guidance and check that each criterion has an observable pass condition and an evidence destination. Vague outcomes such as “everything works,” missing acceptance verification, stale tasks, unavailable native entries, or changed unreviewed scope block readiness.
4. Check that GOAL links the installed [delivery skill](../change-deliver/SKILL.md), applicable project guidance and the selected native implementation entry. If commit/push/MR follow-up is in scope, confirm its authorization, platform/project and existing tools/check/reviewer configuration. Record any missing destination or prerequisite instead of inventing one.
5. When blocked, report each relevant file, unmet criterion, native prerequisite or approval gap, and the concrete correction needed. Hand off to [change-prepare](../change-prepare/SKILL.md) or the approver and direct the developer to rerun change-ready. Withhold **Ready for implementation** and every runnable implementation command, including `/goal` and compatibility delivery commands.
6. When every criterion is met, report exactly **Ready for implementation** and the following copyable command, substituting the actual repository-relative GOAL path (never an absolute path, template placeholder or example path):

   `/goal Implement the reviewed change in "<actual-repository-relative-path>/GOAL.md" and verify every completion criterion in that file.`

Emitting the ready-produced command grants no approval. The developer's later submission of that exact `/goal` is the separate act of starting the already approved scope; it cannot satisfy missing approval or waive extra native prerequisites. Changed scope requires review and approval again. Hosts without `/goal` use change-deliver with the same GOAL and approvals.

These skills guide an agent that loads them. They cannot enforce a write restriction when a host or agent bypasses the skill; host permissions control filesystem access. A request to hurry or skip the process does not establish a missing prerequisite after this skill is loaded.

# CLI 初始设置交互参考

研究日期：2026-11-03。对象：Rigup 的首次设置、更新和恢复。
本文只记录官方资料中的交互事实及本项目设计推论，不是工具兼容性验收。
核验方式：Context7 检索 OpenCode 官方资料，再用官方站点逐项复核；Vite 查阅官方指南。

## 1. OpenCode：连接能力与项目初始化分开

以下记录的是 `opencode.ai/docs` 的终端交互。该入口当前注明 OpenCode 1，另有 OpenCode 2 文档；不能据此推定两个版本的实现完全一致。[官方介绍](https://opencode.ai/docs/)

- 在项目目录执行 `opencode` 会进入 TUI，也可以显式传入项目路径。[TUI](https://opencode.ai/docs/tui/)
- `/connect` 负责选择 provider 并接入凭据，`/models` 单独呈现可选模型；连接与模型选择不是项目规则生成。[TUI 命令](https://opencode.ai/docs/tui/#commands)
- 官方入门把 provider 配置放在项目初始化之前，之后在项目中执行 `/init`。[入门](https://opencode.ai/docs/#configure)
- `/init` 扫描重要文件，对仓库无法回答的问题定向提问，创建或更新 `AGENTS.md`，内容以命令、架构、惯例及已有规则引用为主。[Rules](https://opencode.ai/docs/rules/#initialize)
- 凭据与普通配置分开存放；官方列出的 `/connect` 凭据位置是用户目录的 `auth.json`，不是项目 `AGENTS.md`。[Providers](https://opencode.ai/docs/providers/#credentials)

配置层级也与项目初始化分开：全局偏好、项目配置、运行时覆盖及管理员配置可共同参与。它们按键合并，冲突按优先级处理，而非用项目配置整体替换全部配置。[Config](https://opencode.ai/docs/config/#locations)

对 Rigup 的启发：

- “这次用什么模型研究项目”和“把配置安装给哪个 coding agent”应是两个问题。
- 可以先识别现有配置和缺口，再询问无法推断的选择，减少填写技术栈、检查命令等重复信息。
- 提供明确的项目设置入口，但不必复制 OpenCode 的长期聊天会话和全屏界面。
- 只借鉴凭据与项目配置分离；首版仍沿用已确定的环境变量引用，不自动读取或迁移其他 agent 的登录凭据。

## 2. create-vite：向导与参数共用一个目标

`npm create vite@latest` 提供交互提示，也可以直接指定项目名称与模板；`.` 表示当前目录，`--no-interactive` 可关闭提示。[Vite 官方指南](https://vite.dev/guide/#scaffolding-your-first-vite-project)

对 Rigup 的启发：

- 交互向导和参数化运行应生成同一种有效选项，调用同一条 analyze/generate/preview/apply 主线。
- 目标目录应尽早可见，不能等生成完才发现改的是 monorepo 根目录或错误子目录。
- 无 TTY 时不等待键盘输入；缺少必需选择就返回字段与下一步，而不是偷偷采用高影响默认值。
- 首版完成设置后退出，把后续开发交给已安装资产和用户所选宿主。

这些是本项目取舍；并非声称 create-vite 与 Rigup 具有相同的合并保护、安装恢复或权限模型。

## 3. 建议的首次设置主线

```text
rigup / rigup init
  → 确认项目目录与作用范围
  → 只读识别现有配置、代码和检查入口
  → 选择分析方式，并验证所需输入
  → 选择目标 coding agents
  → 选择 SDD、知识工具和可选反馈接线
  → 汇总研究范围、模型使用及预算，开始研究
  → 生成候选并预览具体改动、安装任务和待办
  → 在已有授权范围内执行，必要时作一次最终确认
  → 分层报告结果、给出宿主重载/下一步后退出
```

其中 `rigup` 的无参数行为属于待设计的新入口；现有架构的 init/update/doctor 命令仍是基础。
建议显示阶段名称而非强制固定页数：不需要的条件问题直接跳过，返回修改时只重做受影响的候选。

模型方式需要明确分支：

- 独立模型：首版只展示已经实现的 provider；检测环境引用是否存在，验证模型连接后再读取/发送项目材料，不由目标宿主选择推定 API 登录有效。
- 宿主方式：导出过滤后的结构化请求，说明在当前宿主中完成及回传/续跑步骤；没有响应就是待续跑，不显示分析完成。
- 无有效模型：允许返回设置或保留私有草稿，不以模板占位冒充动态分析完成。

模型调用前显示发送范围、过滤/拒读规则与预算；网络验证不默认发送仓库内容。不得将 API key 写入可提交配置或终端记录。

## 4. 更新、冲突与恢复的交互原则

- 已安装项目再次进入，应显示当前选择和待办，提供更新/诊断入口，避免重新填写完整初始向导。
- update 以现有配置为起点，保留版本与用户选择；升级、移除能力需要显式意图，不能因重新检测未发现就删除。
- 预览必须列出最终文件改动、结构化操作、目标目录、副作用和冲突，不只显示“推荐配置”。
- 预览无冲突才进入正常执行；需要人工处理时展示具体片段和重新预览方式，不暗中选择覆盖。
- 中断重进先对账：区分已完成、失败、结果未知与未执行，再给出继续入口，不能把“重新运行”等同“重新创建”。
- 生成缓存命中仍需比较完整目标摘要；研究输入排除生成物，不等于忽略用户对托管配置的修改。
- doctor 默认只读，项目检查按显式选择运行；配置已写好、工具初始化、宿主加载、软件测试和 Agent eval 分列。

以上规则来自本项目既有设计；外部工具仅提供交互模式参考，不替代本项目的保护契约。

## 5. 不照搬的部分

- 不把 `/connect`、`/models`、`/init` 原样扩张成长期驻留的聊天命令体系。
- 不因参考工具支持多 provider，就承诺 Rigup 首版已有相同模型矩阵。
- 不从“发现 agent 可执行文件”推导“宿主已经加载 skills/MCP”，也不从静态配置存在推导连接成功。
- 不为了完成向导而搭建客户测试环境、生成业务测试或默认启用发布能力。
- 不额外建设用户账户、凭据库或后台服务；已有环境变量引用和项目配置足以承载首版选择。

## 1. 范围与复杂度取舍

脚手架只在 setup/update 时运行：分析项目、生成配置、展示差异、安装验证后退出。skills、hooks、MCP 和客户 CI 安装后独立使用，不调用脚手架。

首版保留四件核心事情：理解项目规范与模式、按需生成内容、适配工具、保护用户修改。所选四种 agent、三种 SDD、OpenWiki/CodeGraph、自定义 skills 和反馈接线的需求不变。

本轮简化：

- 七个模块合并为四个，能力选择是普通配置映射，不建设通用依赖解析平台。
- 只保留项目画像、安装计划、安装清单三份主要数据，不公开多层中间协议。
- 直接安装项目资产，移除内容寻址 bundle、多版本激活指针和不可变安装清单系统。
- 生成按串行清单推进，用简单缓存恢复，不建设并发 worker/分布式任务系统。
- 更新采用基线比较、差异预览和逐项记录，不承诺多文件/远端整体事务。
- skills 复用所选 SDD 的产物和进度，不附加自有研发状态引擎。

明确取舍：首版不支持热更新正在使用的配置，不协调跨 worktree/多机器的并发升级。实际 apply 前由开发者结束会加载待改资产的 agent 会话，更新后按宿主要求重载；host 可先完成只读研究及最后响应，再退出会话并从独立终端续跑。脚手架不读取、重置或迁移研发进度。

建议使用 TypeScript/Node.js、单进程 CLI、项目级配置优先；具体库与上游版本在实施时锁定。

## 1.1 整个脚手架的确定性与 agent 边界

Rigup 是确定性 CLI/集成/安装骨架，加上有边界的项目理解与内容生成。不是所有项目资产都由 agent 生成。“固定”指产品规则、格式和可执行结构固定，值仍可来自用户选择、静态扫描及经过核验的项目配置，不等于硬编码所有项目内容。

### 确定性代码与模板负责

- **CLI：** 命令解析、配置优先级、向导章节/条件、TTY/JSON、预检、授权范围、进度、退出码与报告结构。可探测事实由代码展示，用户选择按明确规则处理，不让模型临时设计向导或决定权限。
- **静态发现：** 目录/Git/worktree、manifest、已知配置格式、已有命令、工具版本、原生入口、路径和文件摘要；从已知格式提取事实，不需要模型“生成”。未知格式可报告，不能把猜测当静态发现。
- **集成 recipes：** 四宿主的路径/格式、三 SDD 的原生绑定、工具安装/初始化/MCP、检查与 GitLab 接线由版本化实现维护。模型不能创造上游命令或临时编写新适配器来执行。
- **资产渲染：** JSON/TOML/YAML 机器字段、MCP 参数、hooks/CI/辅助脚本、manifest/baseline、技能 frontmatter 与公开入口、原生 SDD 调用和不可取消 gates 使用模板/代码；所选 agent/路径/命令/envRefs 是参数。自定义 skills/scripts 原样复制，不经模型重写。
- **安装更新：** 所有权、差异/三方合并、目标前置校验、锁、备份、固定顺序执行、取消/对账/恢复与原子提交都由代码负责；模型不裁决覆盖/删除授权或绕过冲突。
- **验证事实：** 配置解析、链接/引用/摘要、工具探测、命令执行与退出状态、真实结果记录由代码完成。doctor 默认不调用模型；接入与项目检查分开，不由模型宣布通过。

### 需要 agent 理解和生成

- **理解已有材料：** 判断已有文档/rules/skills 表达了什么、适用于哪里、是否满足本次接入、哪些内容冲突或缺失。文件存在性可静态判断，内容是否足够通常需要语义理解；不能仅因有 README 就跳过研究。
- **补缺研究：** 对缺少规范的主题调查真实代码，比较同角色实现、独立支持与反例，形成带范围和不确定性的模式/惯例；不生成 AS-IS。
- **动态产物规划：** 在产品允许的文档/references 范围内，决定需要补哪些主题、粒度和研究起点、哪些现有来源只需引用。必需资产、公开 skill 集合、安装目录及可执行操作不是由模型自由决定。
- **项目专属正文：** 将可用结论写成开发约定、适用情形/范例/例外，以及 skills 中必要的项目语义上下文；摘要要指回原来源。已有正文足够时复用，不重新生成全文。

上述沿用 OpenWiki 的研究/规划/逐项生成方式，共用受限 reader/backend。agent 返回结构化观察、引用/产物建议和私有文本候选；代码验证后才进入确定性渲染和 Installer。语义充分性可用 agent 检查，结构/来源校验与真实执行结果仍独立判断；模型判断不充当安装授权。

### 混合产物如何组装

以 change-deliver 为例：入口、步骤顺序、原生 SDD 调用、检查/恢复要求和 gate 由模板固定；项目检查命令及文档路径由配置/发现/集成绑定；agent 提议的局部约定放在有范围的 references，由固定步骤按任务读取。候选若指示跳过 gate、改变步骤/权限或与固定流程冲突，拒绝接受并有限重做，不能靠保留固定段落就认定安全。AGENTS.md 同样由确定性导航/命令块与必要项目约定引用组成，不整份交给模型自由生成。语义冲突检查仍需真实宿主验收，文字指引不是宿主外部的权限强制器。

hooks、CI 与机器配置只消费经过 schema/来源校验的参数；不从模型 Markdown 中提取 shell 直接执行。若客户尚无适配器，记录待接入或由开发者另行实现，不让 setup agent 临时生成可执行集成。动态候选也不能扩充用户所选能力或写入范围。

### 用户/客户决定与外部工具负责

agents/SDD/工具选择、必要的命令确认、读取与执行范围/预算、凭据引用、部署目标、政策和冲突裁决来自有效配置与用户/客户授权。模型可提出推荐，不能替用户新增选择或批准。AS-IS 由 OpenWiki、代码索引由 CodeGraph、项目测试/eval 由客户已有体系负责；安装后的研发 skills 由宿主 agent 执行，不由脚手架常驻调度。

### 哪些操作不需要模型

help/version、配置校验、静态探测、默认 doctor、已有 Preview 的 apply、集成模板渲染和具备明确参数的工具接线都可不调用模型。若本次范围只有确定性安装/接线、或匹配缓存已包含全部必需语义结果，则 init/update 无须重新研究。模型凭据只在实际需要独立模型任务时预检，不给纯确定性路径增加无关凭据要求。

是否存在必需语义任务由显式选项、已知接入信息和有效缓存决定，不新增一个“跳过 AI 即视作已理解”的模式。已有文档但语义接入尚未核实时仍属于研究任务；缺少后端时按既定输入/待续跑规则报告，不生成泛化占位正文或伪装分析完成。单次 init 可同时含确定性资产与语义资产；后者必须满足原计划的必需项验收，不能以工具装好替代。

## 2. 四个模块

1. [Project Analyzer：项目分析](scaffold-modules/01-project-analyzer.md)：合并扫描与语义研究，输出有证据的项目画像。
2. [Rigup Generator：配置生成](scaffold-modules/02-rigup-generator.md)：选择集成，动态规划并生成内容，组装配置和 skills。
3. [Rigup Installer：安装更新](scaffold-modules/03-rigup-installer.md)：合并配置、预览差异、安装初始化并验证。
4. [Integrations：工具集成](scaffold-modules/04-integrations.md)：提供宿主、SDD、工具和客户环境的具体接入方法。

调用主线：

```text
CLI 收集选项
  → Analyzer 分析项目
  → Generator 选择集成、规划产物、生成候选
  → Installer 展示差异、安装、验证
  → 报告结果并退出
```

Integrations 是前三者使用的实现库，不是额外执行阶段。CLI 只串联调用和交互，不复制业务规则。首次接入与更新使用同一条主线。

## 3. 小接口与数据

```typescript
type StepResult<T> =
  | { status: 'complete'; value: T }
  | { status: 'pending-host'; requestId: string; requestPath: string; nextCommand: string };

Analyzer.analyze(root, options, backend): Promise<StepResult<ProjectProfile>>
Generator.generate(profile, options, backend, previousAssets = []): Promise<StepResult<SetupPlan>>
Installer.preview(plan, resolutions?): Promise<Preview>
Installer.apply(previewId): Promise<InstallReport>
```

主要持久数据：

- ProjectProfile：技术栈、模块、已有规范/启动检查命令、环境要求、知识来源/维护者、未知项及输入指纹。
- SetupPlan：候选文件、配置修改、所需安装任务、旧托管项的逐项去向、明确移除项和警告。
- InstallManifest：用户选择、模板/集成版本、生成时已知的模型配置、托管文件/配置块、基线位置和实际安装结果；无法取得的版本标为未知，不猜测。

Preview 是 Installer 对 SetupPlan 加上当前环境差异后的可审阅结果；保存到私有缓存，不另建领域对象体系。只有差异已准备好，才执行 apply；apply 不调用模型临时补正文。

StepResult 只区分完整返回与技术性待宿主，不是第四份主要持久协议。backend.run 同样返回 StepResult；pending 由 analyze/generate 原样向上返回，CLI 保存请求后退出 3，不构造部分成功计划或调用 preview/apply。同一私有 run 保存当前阶段/job、已接受候选、已用预算及授权关联；续跑先复核上下文，再恢复未完成节点。预算耗尽是已有的失败/待输入路径，不能伪装成 pending-host 或完成。previousAssets 是可信 manifest 的只读库存投影，由编排层加载；首次为空，元数据损坏则先诊断，不作干净安装。

研究输入指纹用于判断项目事实是否变化及候选是否可复用；完整目标摘要另用于检查目标是否被修改。研究输入排除自身托管输出，混合配置保留非托管内容；生成正文不反过来成为独立规范证据。统一 reader 在模型调用、宿主导出、search 和证据缓存前过滤普通配置中的凭据，无法安全分离时拒读并列未知项；详见 Analyzer 的读取与投影规则。首版不建立逐事实的精确依赖图；输入变化可以保守地重新生成语义内容。

## 4. 项目资产与私有缓存

```text
.rigup/
  config.yaml              # 用户选择和运行方式
  manifest.json            # 安装清单、集成版本、托管项
  baseline/<installId>/    # 上次生成的托管内容/配置块
docs/rigup/              # 仅在需要时补充工程约定/references，不生成 AS-IS
各 agent 原生目录/文件       # skills、入口文档、MCP 配置
```

不建立 bundles、installations 和统一 flow runtime 目录。SDD、OpenWiki、CodeGraph 保持各自原生布局；客户研发状态由原框架/项目维护。

生成候选、进度、失败日志和写入前备份放在操作系统用户缓存目录，以规范化项目路径区分。缓存可以丢失：丢失后重新生成、检查实际安装和展示差异，不能凭缓存缺失覆盖项目。

同一项目的研究、请求导出、生成和 apply 共用一把执行锁，避免两个进程互改同一轮缓存；host 待回传时完成持久保存后释放锁，下一次续跑重新取得并复核。候选按 runId 隔离。锁及未决写进程/远端操作的阻塞记录保存在用户应用状态目录，区别于可丢弃生成缓存；缓存丢失不解除这些记录。它们仍是既有执行保护，不是研发状态平台。

baseline 只保存本产品生成的内容或拥有的配置块，不复制混合文件中的客户密钥等无关内容。baseline 可以随项目版本管理；缺失/被修改时不伪造三方合并依据。

## 5. 生成、安装与更新规则

### 5.1 动态生成

采用 OpenWiki 的核心做法：先研究系统，再规划适合项目的产物，逐项生成、校验和保存候选。

机器配置、命令和强制流程结构使用集成实现与模板。优先将项目已有规范接到 agent 入口、研发 skills 和已有检查；保留原文及范围，只对缺口调查代码并生成工程约定或必要流程上下文。系统现状正文统一由 OpenWiki 负责；Rigup 只维护其接入状态和知识导航，缺失时报告，不自行生成平行现状文档。目录不是文档目录的机械镜像，也不动态增加未选择的公开 skill。文档按专门的[开发流程标准](2026-11-03-documentation-system-design.md)计算触发条件、消费者和验收要求；复用已有权威来源、SDD/OpenWiki 原生正文，不生成空 glossary/ADR 或未发生的交付记录。

独立模型和宿主 agent 两种方式保留，共用相同输入、任务清单和结果校验；不建设常驻 setup MCP。首版串行生成；引用关系可以成环，汇总文档最后生成，无需通用任务 DAG。

每次更新还核对旧托管库存：新清单之外的旧项也要明确继续维护、更新、提出退役或保留待处理，保持其 ownership 和可信旧基线。已知失效且仍会被入口/宿主加载的规则，未修正或安全解绑时不宣称相关更新完成；省略不等于退役。具体规则见 Generator。客户本地模板和结构化 MCP 输入走同一生成/预览主线，范围及消费例子见 Integrations 第 4 节。

### 5.2 文件保护

记 B 为上次生成基线，L 为当前内容，N 为新候选：

- L 不存在且没有旧 B：创建；有旧 B 时视为用户删除，保留并报告冲突，明确选择恢复后才重建。
- L 等于 N：不写入。
- L 等于 B：更新到 N。
- N 等于 B：保留用户修改。
- 其他情况：可安全合并则合并，否则保留原文并报告冲突。
- 没有可信 B 且文件已存在：不自动接管覆盖。

混合配置只改拥有的键/标记块，保留其余字段与注释。无法安全处理的格式给出待处理片段，不整文件重写。

停用能力产生明确的移除清单。未修改的托管项可以删除/解绑，用户修改过的先保留；没生成不等于授权删除。共享工具不自动卸载。

### 5.3 执行与恢复

按固定顺序执行：安装依赖 → 写入配置/skills → 初始化所选工具 → 验证 → 更新 manifest/baseline。每项执行前确认目标未发生意外变化。

该保护同样适用于外部命令：项目文本先转候选合并；不能预演的初始化只在已确认的新空范围或已核验的工具自有数据范围执行，不能仅因路径已声明就覆盖已有客户文件。与候选目标重叠的外部写入须先消除或转候选，否则不执行。详细执行前置及验证规则见 Installer 第 3 节。

使用上述项目级执行锁和简单进度记录。副作用发出前先持久保存未决操作，崩溃/强杀后的对账规则以 Installer 第 4 节为准。配置/初始化失败或结果未知时停止依赖动作，保留已完成项与备份；仅项目检查失败仍可提交已成功接线的 manifest/baseline，分列失败并退出 1。重试先查看实际结果，不重复创建已存在资源。外部操作超时不当作没有发生，查询不明时报告待处理，不盲目重试。

不提供整体自动回滚。Git diff、文件备份和明确失败报告用于恢复，不自动 reset 用户工作区。manifest 最后原子写入；失败后重跑会结合实际文件和缓存重新规划。

### 5.4 接入验证

分开报告：配置是否写好、工具是否可用、宿主是否需重载、初始化是否完成、项目检查是否通过。

Git hooks/静态工具按用户选择配置，测试只连接已有命令。缺测试、凭据或环境时列待办，不生成测试体系或修业务代码。项目测试失败不等于接入失败。

已有启动脚本、开发容器、隔离目录和环境检查可以识别并接入；测试数据、环境建设、身份和网络策略由团队提供。安装配置成功不表示项目已经能运行。

软件验证与 Agent 评估分别报告。已有 Agent eval 命令可按选择接入 skills/模型/工具配置变更的检查；评估任务、独立验收用例和通过策略由团队维护，脚手架不建设评估平台。没有 eval 时标为未接入，不把项目测试通过当成 Agent 稳定性已证明。

### 5.5 轻量的使用约定

生成内容采用分层引用：入口文档保存命令/知识导航，模块规范按需加载，skills 保存流程，工具连接提供实时信息。来源系统和维护者已知则保留引用，未知则列待办，不把所有正文复制进每个 agent 入口。

研发模板在原有 SDD 文档或工单中补充任务约定：目标与来源、允许修改/操作范围、验收、环境依赖、预算/停止条件、负责人及失败接手人。简单任务简写，复杂/高风险变更再展开设计，遵守客户及上游必需规则；不新增一份强制任务协议文件。

风险规则和自动化权限来自客户政策，脚手架只接入。项目说明、skills 和本地 hooks 是引导/检查，不能代替受保护 CI、仓库身份和生产权限。配置默认不扩大授权；未知规则不由模型自行批准。

用已有工单号或分支标识关联方案、commit、检查报告和发布记录。记录可留在 Git/MR/CI 中，不建立新数据库，不默认复制完整日志/会话。运维反馈回到普通需求/缺陷入口，不增加常驻监控服务。

这些信息优先引用已有记录，只要求所选能力必需的输入；其余未知项列待办，不把整套组织建设清单变成 setup 的必填表。

## 6. CLI 与验收

主要命令：rigup init、rigup update、rigup doctor。init/update 在耗时步骤前集中收集选择、预检并确认本次执行范围；默认在该范围内连续研究、生成、自动保存差异并安装，不在生成后重复询问。用户也可在启动前选择生成后审阅。实际 apply 始终校验具体 preview 与授权一致；越界或真实冲突保存后报告停止。--dry-run 只准备候选与差异。需要分步自动化时再暴露 plan/apply，不先设计八个独立用例。再次运行同一命令可复用匹配缓存并恢复。

执行期间持续显示阶段/子任务、真实完成计数、下一步与是否需要用户操作；整体进度和剩余耗时按有依据的估算区间展示，无样本时明确待估算。静默长任务提供存活与等待原因，重试/阻塞不假装完成；具体规则见 CLI 交互设计第 7.1 节。

首版验收：

- 同项目可以安装多个 agent，配置不互相覆盖。
- 所选 SDD 能力是真实绑定，无法满足时明确报告，不伪造命令。
- 新项目无源码时不生成虚假现状；无 Git 可分析，用户选择后才初始化。
- 规范和文档结构能随项目变化，必需产物未生成不能报告成功。
- 旧项目的配置、原 hooks 和用户修改被保留。
- 重复安装无重复项，中断重试不盲目重复外部操作。
- 没有脚手架 CLI 时，已安装资产仍可独立使用。
- 更新不读取/改写研发状态；更新期间不承诺正在运行的会话继续使用旧配置。
- 四宿主/三框架及工具版本的兼容性以实际测试为准，阶段演示不代表全部完成。
- 环境、软件检查和 Agent 评估的接入/结果分开，缺失项不伪装成已验证。
- 普通配置内的凭据不进入模型/宿主请求或证据缓存；未知敏感格式拒读并报告。
- 输入和版本不变且缓存完整时，连续 update 不因自身输出而重新生成差异；托管项的用户删改仍进入合并/冲突处理。
- 真实模型分别在单服务与 monorepo 完成研究、动态清单、正文生成及源码变更后更新；核实引用、未知项和项目差异。独立模型与宿主方式分别记录验收状态，缺凭据/环境时为 pending，不能以模拟协议或宿主连接成功代替。此验收验证脚手架生成能力，不建设客户 Agent eval 平台。
- 任务约定、接手人和证据引用落在现有产物中，项目风险策略仍由客户决定。

以后确有需求再加入：多版本并存、热更新、跨项目升级协调、精确生成依赖图、并发 worker 和自动补偿事务。这些都不是首版前置条件。

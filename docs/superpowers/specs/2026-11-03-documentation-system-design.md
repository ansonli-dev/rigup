# Rigup 开发流程文档与生成标准

日期：2026-11-03。状态：按用户反馈收缩为支持开发流程的最小文档；尚未实现。

关联：[总设计](2026-11-02-rigup-design.md)、[Generator](scaffold-modules/02-rigup-generator.md)、[研发 skills](2026-11-02-installed-skills-design.md)、[实施计划](../plans/2026-11-02-rigup-implementation.md)。本文约束客户项目中的开发文档，不要求复制 Rigup 自身的文档目录。

## 1. 范围

优先复用项目已有开发规范并接入 harness；只有缺少或不够用的部分才调查代码、提炼模式和约定。已有文档是否复用以内容、作用域及具体开发用途判断，不以是否叫 conventions.md 判断。

本设计的重点是让已有规范和补充识别的约定都能用于下一次开发；文档只是承载方式。难点和验收核心见 [Analyzer 的模式识别设计](scaffold-modules/01-project-analyzer.md#21-从代码识别模式并提炼约定)。AS-IS 全部由 OpenWiki 负责，不属于这里的研究和生成目标。

文档服务于开始任务、实施、检查和交付。判断是否需要一份文档，要能说明哪个开发步骤会读取它、读完能作什么决定或执行什么操作；只为分类齐全、留档或展示而写的文件不生成。

保留三类用途：项目开发指南、流程执行指引、本次变更的工作文档。它们不对应三个必建目录：开发指南尽量短，流程写入已有 skills，变更沿用原生 SDD。setup 生成前两类必要内容并配置第三类的落点；第三类在真实任务发生时由研发 skills 维护。

此前的八类方案扩大了文档范围，本轮改为围绕开发步骤组织。将现状、验证指南、交付记录等各自设成默认文档会与 OpenWiki、skills、MR/CI 重复，因此不继续保留这些独立生成类别。

## 2. 三类用途与生成标准

### 2.1 项目开发指南：在这个项目里怎么改

**谁读、何时读：** 开发者和 agent 开始任务、编码或评审时读取。

**最低内容：** 有效的构建/启动/lint/test/eval 命令及 cwd/环境引用、需要遵守的工程约定和适用范围、常用实现范例的路径、所选 skills 与 OpenWiki/CodeGraph 查询入口。缺少的能力简要说明，不生成对应空章节。

**来源：** 现有项目规范、配置、真实命令入口及经模式识别研究核实的代码惯例。每条推断保留支持与反例、样本范围和未知项；先做同角色比较和反例搜索，再决定可否作为约定。显式规范、常见惯例、局部模式、建议分开；单个实现不升级为全项目规则，规则与实现冲突时并列报告。已有检查则链接命令，没有检查就不声称已强制执行。

**生成标准：** 指引应回答“新增同类代码时怎么写、参考哪里、什么情形不适用”，例如“订单模块新增 handler 时沿用已核实的错误转换入口，参考实现 A/B；后台任务尚未验证适用”，而非“统一错误处理”。未决冲突保留待决，不擅自挑一种写成全仓规则。优先在 AGENTS.md/CLAUDE.md 等原生入口放必要摘要和引用；约定较多且需要按模块加载时才拆 references 或 conventions.md。多 agent 共用同一正文。正文应能指导具体改动，避免通用口号、现状百科和重复工具手册。命令由确定性集成提供，不由模型发明。

**更新标准：** 命令、工程约定或能力入口变化时重核；只更新拥有部分，保留用户修改。空项目记录已有命令/已知约束和必要缺口，不伪造范例、模块或已通过的检查。

### 2.2 流程执行指引：这一步怎么做、做到什么程度

**谁读、何时读：** coding agent 执行 change-prepare/change-deliver，以及实际选装的 change-release 时读取。

**最低内容：** 本步骤输入、原生 skill/命令及执行顺序、需要读取/更新的产物位置、完成条件、检查与失败处理、必要的人类决策点。授权、预算、停止条件和接手人沿用实际任务与客户规则。

**来源：** 锁定的 SDD 原生入口/gates、项目开发指南、客户 skills 和实际集成。所选检查注明命令、cwd、环境引用、前置条件和副作用；详细操作按需放在 skill references 中。

**生成标准：** 直接写入 skills 及必要 references，不另生成一份同内容的 workflow.md、testing.md 或流程总手册。保留上游必需 gate，已有授权的连续步骤不机械拆开。无 SDD 时仅接入用户选择的工具/自定义流程；无部署适配不生成 release。自定义 skill 原样保留。

内置 skill 的步骤及读取时机固定，模型正文和客户模板只能进入有范围的 references；不能替换流程或以相反指令绕过 gate。接受检查遇到此类冲突须拒绝/有限重做，验收检查实际读取后的行为，不只检查固定文字是否存在。客户模板的输入和目标范围以 Integrations 第 4 节为准，不扩大本文的 setup 文档类别。

**更新标准：** 选择或锁定的入口变化时更新绑定，普通 update 不隐式升级上游，不读取或迁移研发进度。仅输出实际消费者需要的 tracker/documentRoutes/labelMapping，引用工单系统不等于已完成可执行适配。

### 2.3 变更工作文档：这次要改什么、怎么做、如何验收

**谁读、何时读：** change-prepare 编写，开发者确认必要决策，change-deliver 按其实施和更新。

**最低内容：** 需求包含问题/来源、预期行为、范围/约束和验收；设计补充必要的接口/数据流、方案取舍与兼容/恢复；计划列可执行任务及验证方法。允许操作、预算/停止条件和接手人按任务需要写入同一权威记录。简单改动可以在同一工单里简写，不强制拆多份文件。

**来源：** 用户/工单、OpenWiki 与实际代码调查、客户政策和已确认决策。业务目标、待选方案、已作决定和未知项分开；不能从代码倒推业务需求或历史批准。

**生成标准：** 沿用 Superpowers/OpenSpec/Spec Kit 的原生产物及其要求，不再叠加 Rigup 的 intent/design/plan 文件。无 SDD 时沿用项目工单或既有记录，不新增一套强制协议。只有实际任务发生才写正文，setup 只配置可用落点与引用。

**更新标准：** 实施进度更新原生任务；范围/验收变化时重新核实授权。检查命令、commit、环境、结果/报告及未验证项写入现有任务/MR/CI，足够交接即可，不强制另建 verification.md、delivery.md 或审批账本。新代码不能沿用旧对象的通过结论。

## 3. 其他信息各归其位

- **系统现状：** OpenWiki 负责生成和更新。Rigup 只接线、引用、报告覆盖/新鲜度缺口；不可用时不回退为生成 context.md、架构百科或模块现状页。
- **代码结构查询：** CodeGraph 提供索引与查询，不复制成另一套文档。
- **术语、ADR、业务材料、运维手册：** 有现成权威来源且本次开发需要时引用；实际任务需要新决策/说明时按项目惯例补充，不列为 setup 默认生成项。
- **安装与维护：** 简短使用/更新说明放已有 README 或入口合适位置，实际安装状态来自 InstallReport/manifest；不因此生成一套客户项目维护文档。
- **交付、发布和反馈：** 使用已有工单、MR、CI、发布平台及适用 runbook；skills 提供执行/交接要求，不预生成尚未发生的交付或事故记录。

## 4. 已有规范如何接入 harness

复用不只是留一个总链接：要让规则在相应开发步骤被读取，并与已有反馈方式相连。

- **agent 入口：** 在原生入口的托管导航块列出规范来源、适用目录/任务和何时读取；已有等效导航则复用，不叠加重复块。模块规则保留局部范围，多 agent 指向同一原文。
- **change-prepare：** 按任务范围读取相关规范，作为设计约束和验收依据；未决冲突保留在原生任务中，不由生成器替团队裁决。
- **change-deliver：** 编码前加载适用规范及真实范例，检查/评审时引用同一来源，避免实现和评审使用两套规则。原文足够就直接引用，补充 references 只说明原文缺少的调用上下文。
- **反馈接线：** 有 lint/test/架构检查等现成命令时，按选择绑定 hooks/CI/skill；只有文字规范时由 skill 指引实现和评审，并明确未自动执行。setup 不因发现文字规则而生成客户测试或强制检查器，不把“已引用”报成“已强制”。

例如已有 docs/backend-guide.md 描述错误处理，Rigup 在 agent 入口标出后端任务应读取它，prepare 用其核对方案，deliver 按其实现和评审，并连接已有检查命令；不另写一份 error-handling.md。若它没说明异步任务，只对这个缺口调查代码并补带范围/证据的参考。

接入关系使用 ProjectProfile/SetupPlan 已有来源与引用信息表达，不建立新的规范平台或持久映射数据库。原文保持非托管，Rigup 只记录其自身导航/skills/配置块的所有权。本地原文变更进入研究输入指纹，移动/删除后更新接入引用或报告失效，不保留死链接；远端版本未知时不把旧核实结果当本次有效内容。

远端内容复用前按已有适配重核版本/摘要；无可比版本时本次重读，不能重读则列 unavailable 并使依赖该内容的缓存失效。旧托管指南/导航也须按 Generator 的库存规则逐项核对；新清单遗漏不能让已知失效规则继续被引用或自动加载，也不能丢掉其 ownership。仅保留不可读 URL 导航时明确内容未核实。

验收分别判断：来源是否可用、适用规则是否能从实际入口/skill 找到、已有检查是否真的接通。Installer 第 2 节还须对最终合并/保留内容检查所选能力的入口、绑定和引用，不能只检查生成候选。配置可解析不等于宿主已加载，引用可达不等于规则已自动执行；真实宿主验证仍单独留证。

## 5. Generator 的最小生成契约

研究与生成流程沿用 OpenWiki 的方式：先发现已有规范和待调查主题，再动态规划产物，每项继续调查、形成候选、校验接受，最后汇总。这里只改变研究侧重点、产出物和接入位置，复用/模式识别规则是研究任务要求，不单独建设另一套流程。具体对应见 [Analyzer](scaffold-modules/01-project-analyzer.md) 与 [Generator](scaffold-modules/02-rigup-generator.md)。


不增加文档类别注册表。现有 ArtifactJob 保留 logicalId、目的、研究起点和相关产物，只补 consumer（具体使用步骤）、required/reason、sourceRefs、acceptance；target/ownership 沿用原安装意图。只允许规划 setup 所负责的开发指南、所选 skill 及必要 references；变更工作文档由安装后的 skills 在任务中维护，不进入 setup 的正文任务清单。

先判断已有来源是否足够，再补具体使用步骤缺少的内容。每个候选至少通过以下检查：

1. 有实际消费者和用途，已有正文足够时只引用；不为满足类别或固定数量建文件。
2. 事实可沿 reader 证据核实，命令/能力绑定真实；未知与建议不伪装为规范、批准或成功结果。
3. 内容足以支持对应开发步骤；必需信息不能用占位模板代替。缺少测试/eval 就说明未接入，不生成业务测试体系。
4. 本地引用可解析，必要 references 从入口/skill 可达；不复制 OpenWiki 或 SDD 正文。
5. 确定性格式/路径/来源检查与语义充分性分开记录。必需项不足时有限重做，预算耗尽不宣称完成；可选项按既定策略省略并报告。
6. 不泄露凭据、不越界、不执行源码指令，继续遵循所有权、三方更新和删除保护；省略不授权删除旧文件。

沿用原生布局和现有同用途文件；确需额外约定页时才使用 docs/rigup/conventions.md 等兜底路径，不默认生成 index/context/verification/usage 全套。文档标准版本进入生成缓存及宿主请求绑定；生成内容不成为自己的权威输入。

## 6. 验收与参考

验收首先看是否识别对了模式及边界：支持/反例真实、没有把样板复制算独立证据、局部模式不泛化、配置/规范与实现冲突可见、证据不足能保留判断；再看提炼出的指引是否足以支持新增同类实现。验收同时检查能走通开发流程：入口找到相关约定和工具；skills 能定位实际输入/产物并执行真实检查；变更记录足以说明范围、任务和验收。空项目无假现状/结果，单服务不堆文档，monorepo 保留模块 cwd 与局部规则，多 agent 不复制矛盾正文，已有文档不重复生成，更新继续保护用户修改。

Task 5 落实最小生成契约；Task 9 用真实生成与开发流程定位样例检查可用性。宿主/工具兼容仍独立验收，不由文档存在推出可用。

参考《建立 AI Native 研发体系》（历史本地输入，未随本仓库分发）的交付物交接思路，以及 [Birgitta Böckeler 的 harness engineering 文章](https://martinfowler.com/articles/harness-engineering.html)中 guides 与 sensors 配合的思路（2026-11-03 已读取）。这里的三类用途是 Rigup 按开发流程作出的取舍，不将参考文章扩展为客户必须建设的文档体系。

# Open issue integration design

Date: 2026-11-12. Baseline: `20c67fe90b1c88400f076fe5d445821d0fb771f7` (v0.4.1 installer/main).
Requirements: [all open issues #45–#54 and their comments](2026-11-12-open-issues.md).
This design precedes the reviewed execution plan. Existing failing regression prototypes are evidence, not completed implementation.

## Intent and scope

Resolve every open issue together, preserve existing project work, and release the verified result. The developer explicitly authorizes dependency/environment setup, local test resources, version upgrade, merge and release after validation. Claude's real-host validation is delegated to the developer's other Windows computer; deterministic Claude configuration/probe tests still belong here.

Use Superpowers for design, independent adversarial review, TDD and completion verification; codebase-design for small interfaces with cohesive implementation; Ponytail for the smallest complete change. Review design and execution plan separately in multiple rounds. Each round reads the full immutable document snapshot and relevant current source; a patch-only recheck does not count as a clean full round. Fix confirmed findings, record rejected findings with evidence, stop after a full clean round following at least two complete rounds. “Clean” means no actionable known findings, not proof of absence of all possible defects.

## Approaches and selected design

1. Patch each reported message/fixture independently. Small initially, but repeats environment rules and leaves caller-specific drift.
2. Reuse the existing workflow, installer and provider loop, concentrating shared policy in their current interfaces plus one runtime-input module. Selected: solves the ten issues without a second setup engine or new MR platform adapter.
3. Build a new workflow/runtime orchestration framework. Rejected: broad migration and public surface without an issue that needs them.

Preserve the current CLI, protected B/L/N update model, recipe verification, model read policy and native artifact layout. No new dependency is required. Semantic text equivalence never replaces immutable full-file snapshots for preview approval or recovery.

## A. Native change handoff and delivery (#45)

Install three fixed public skills per selected host: change-prepare, change-ready and change-deliver. Reserve all three against customer entry collisions. Keep change-release behavior unchanged.

change-prepare ships a fixed `references/GOAL.md` template and creates a change-scoped GOAL in the native artifact location. It links all current native Spec and Plan files (including split artifacts), identifies the exact change ID and approved scope, selected native implementation entry, project guidance and existing commands/cwds, observable completion criteria and evidence. It does not replace or invent an alternative native spec/plan layout.

The reviewed write scope enumerates every repository-relative file delivery will modify and its purpose, including business changes, applicable native task status/checkboxes and actual evidence destinations. GOAL is writable only for an explicitly reviewed, defined record write. Readiness before emitting a command and delivery before editing reconcile planned writes against that same scope. Delivery's first read-only gate independently derives the planned paths and purposes from GOAL completion criteria, evidence destinations and native tasks/apply instructions, lists them in the handoff, then compares each against reviewed scope before considering current implementation approval. An omitted planned destination is a path-specific blocker requiring preparation, review and scope approval, even when the current request explicitly authorizes that path; stop before any edit, task checkbox or verification record write. Older GOALs with equivalent complete scope and evidence need no formatting migration. Explicit approval of the full current revision/scope can coexist with separate additional authorization, which remains unused outside the reviewed scope; it cannot repair omitted planned writes. A current approval may supersede an older pending record without editing GOAL. Unapproved work, other revisions, incomplete or different approval scopes remain blocked.

Before handing each artifact to the developer, run applicable native review and fill Rigup coverage gaps; fix resolvable findings. Revisions propagate across spec, tasks, verification and GOAL. Native status/instructions determine prerequisites: OpenSpec's isPlanningComplete=false or missingPrerequisites withholds readiness, even if an author considers a file optional. Other selected workflows use their own installed prerequisite commands and approval gates.

change-ready is read-only. It verifies references stay within the repository and resolve to the same current change, every material acceptance criterion maps to implementation and verification, completion is observable, prerequisites and required approvals are satisfied. It reports file-specific corrections and emits no implementation command when blocked. On success it emits exactly “Ready for implementation” and a copyable `/goal Implement the reviewed change in "<actual-repository-relative-path>/GOAL.md" and verify every completion criterion in that file.`

The GOAL points both Codex /goal and compatibility change-deliver at the same installed delivery skill and project guidance. Implementation approval must explicitly cover the current reviewed change, revision and scope through the current human instruction or an applicable, verified project-designated approval record. Missing, pending, stale or scope-mismatched approval withholds readiness and every runnable implementation command even when native planning is complete. Emitting a ready-produced command grants no approval; the developer's later submission of that exact /goal separately starts the already approved scope. Extra native prerequisites still apply, and changed scope requires review and approval again. Hosts without /goal use change-deliver with those same reviewed artifacts and approvals. Read the applicable rules, inspect shared consumers, implement native tasks, run required verification, and record actual results.

Every push in scope requires reviewing outgoing commits against approved scope, fixing confirmed findings and rerunning affected checks before pushing. When GOAL includes MR follow-up, use only project-configured tools (customer commands, native MCP or documented CLI) with a confirmed platform/project. Consume existing CI/reviewer configuration; Rigup does not create CI, review bots or merge policies. Track current MR head SHA; required checks must all pass, configured AI review must explicitly complete, and every finding has a disposition for that head. Re-read head before completion. Pending reviewer plus empty discussions is not completion; an older green SHA is not current evidence. Confirmed findings inside scope are fixed locally, tested, pushed and followed again. Disputed findings require evidence; scope expansion returns for review.

These skills guide agents; they do not control host write permissions or override the host's instruction hierarchy, even after loading. Test both loaded-skill bypass wording and a no-skill boundary and state the enforcement limit accurately. Ordinary missing prerequisites or approval still require a read-only, actionable refusal. An explicit bypass experiment records observed refusal, host override, or unverified execution separately; unverified execution is incomplete evidence. Historical failed bypass attempts retain their original outcomes. This clarification records the observed boundary and does not weaken ordinary readiness or delivery gates.

## B. Declared runtime inputs and setup report (#46)

One runtime-input module owns declaration, read/precedence, private incremental template writes and sanitized summary. Its public interface is:
- `runtimeSetupSummary(root, options, evidence?)`: read-only presence/source/destination/verification records, never values.
- `applyRuntimeInputs(root, options, evidence?)`: lock-held, apply-only private file update, returning the same summary.
- `runtimeEnvironment(root, options, consumer)`: only values explicitly declared for the selected local consumer, layered over its existing essential system environment.

Declarations derive from enabled capabilities and existing config, not arbitrary shell variables. Destinations are local `.rigup/.env`, agent host or CI runner. Declare required/optional and activation reason. A clean local foundation with no external capability needs no credential. CLI provider selection uses its current variables and private settings; provider/model/base URL/output cap remain configurable. MCP processes started by the host and GitLab CI jobs use host/runner env references; a local value never establishes host/CI availability or verification. Host-only model settings are neither imported nor rewritten. OpenWiki's own GitHub workflow remains native-owned.

Seed local entries from explicit effective configuration, trusted repository context and declared ambient variables, leaving unresolved required values blank. Populated local entries outrank ambient values for the same declared input; preserve comments and populated values on repeat apply, fill blanks and append new declarations. Parse dotenv as data, never shell code; quoting round-trips special characters and rejects duplicate ambiguous keys/invalid syntax without echoing values. Local secrets never become SetupOptions, tracked generated assets, baselines, journals, preview diffs, terminal output or JSON report. Preserve undeclared existing entries but never consume them.

Infer a remote target only from a declared platform and unambiguous compatible Git remote, or explicit configured reference. Multiple plausible targets remain input, and no remote action runs merely because a target is found. Local GitLab include generation requires no host/token. Existing unbound custom workflow requirements remain enforced.

Use `customer.commands.environment`, when declared and explicitly selected with `--run-checks environment`, through the existing check runner as a local command consumer. Forward only that command's envRefs plus essential system variables; missing inputs yield pending and do not fabricate an executed check. Expand accepted `${NAME}` argument references only for declared envRefs in a transient argv copy at the final shell-free spawn. Never mutate the reference-only CommandSpec: results, errors, terminal/JSON output and durable check records retain references, and captured output redacts supplied credential values. An undeclared or missing argument reference is actionable pending before dispatch. No expansion in executable/cwd and no shell evaluation. Verify a real child receives a synthetic header value while every persisted/report path omits it, including a failing child that echoes it. Other customer remote operations still require an appropriate configured native tool/adapter.

Write .env only on authorized apply (including an otherwise unchanged update when blanks/new declarations need filling); dry-run and review never modify project files. Use existing project lock, safe-path and private-record protections. Before reading/importing a local file, reject links/hard links, tracked files, overly broad access and unsafe parents. Keep an existing unsafe file unchanged and report corrective action; independent setup can finish pending. Ensure effective Git ignore, including temp files, before copying any credential; a negated ignore rule cannot be assumed safe. Non-Git projects get equivalent managed ignore preparation for a later git init. Atomic writes use 0600 or protected Windows ACL from creation, preserve prior bytes on failure and never store secrets in backups/journals. File creation is idempotent across recovery; private local values are not a managed baseline.

Registry selection is an optional local input `RIGUP_NPM_REGISTRY` for enabled automatic installers (OpenSpec/OpenWiki/CodeGraph). Accept credential-free HTTP(S) URL under existing endpoint safety rules; reject embedded credentials/query secrets. Preserve exact package/version/integrity and package-tree checks. Bind the selected normalized registry identity to the approved operation so changing sources between review and apply needs a new preview; substitute the approved registry only at npm dispatch. Keep default public registry behavior when absent. This does not change the host's package manager settings.

init/update terminal + JSON and doctor share declaration records. Report configuration written, imported variable names and sources, missing inputs with affected capability/destination, and verification remaining. “Configured”, “input present”, “connected” and “executed successfully” are distinct. No implicit provider calls in setup/doctor. Any observed provider count fallback is a capability diagnostic, not a verification claim for future requests.

## C. Provider resilience and evidence safety (#53)

Keep one shared provider loop. For Anthropic, a 404/405 on count_tokens makes counting unavailable for that backend session. Count the actual failed HTTP request once; subsequent turns use a conservative serialized-request UTF-8 byte estimate plus framing allowance, reported as estimated. Other count failures are not silently downgraded. maxCalls continues to count actual HTTP requests, including remote counts; document that it is not a generation count.

Every dispatched generation persists usage as unknown before sending. Require trustworthy usage afterward; unknown usage or excess cumulative budget fails closed. The estimate bounds offered output along with remaining total budget; it does not claim an exact tokenizer count. Output limit defaults to 16384 and is a positive safe integer from RIGUP_MAX_OUTPUT_TOKENS or private provider.json, respecting local declared precedence from B. Both Anthropic max_tokens and OpenAI-compatible max_completion_tokens use min(configured limit, remaining-input estimate). Invalid values name the setting; do not normalize gateway model aliases (send exactly configured model name).

HTTP failures show operation, status and bounded fixed guidance (auth/model permission, missing endpoint, network/timeout) without raw provider bodies, echoed prompts, credentials or URL queries. Diagnostics can include nonsecret structured field/index positions.

A syntactically valid read beyond EOF can return an error tool result with the permitted filtered file's line count, after inventory, scope, link, filtering and read-budget checks. Model retries under the same budget. Do not eagerly read all files just to add counts to list. Other denied/unavailable reads fail closed with safe explanations. Accepted citations still pass the current digest/range/authority validator.

An invalid final JSON or validation result gets at most one repair generation with a safe structural reason and the candidate in the existing conversation. It reuses the same request, reader, authorization and remaining budget; validate again completely. A repair response cannot introduce new tool operations. If repair cannot fit, report the original actionable validation reason. No unbounded retries or silent acceptance.

## D. Discovery, selected executable and daemon policy (#47, #48, #54)

Native discovery isolates every enabled plugin record and manifest, for both Claude and analogous Codex scans. Unavailable unrelated metadata generates a warning naming the plugin and a safe cause, then continues to later records. Missing required native entries remain blockers and version mismatch stays explicit. Warnings flow through the profile into preview/doctor without introducing fake skill identities.

The generated Rigup project launcher embeds the writing package version; new manifest versions records it as rigup. If a trusted local manifest exists, its implementation version must agree with the launcher; a fresh clone can rely on the version embedded in the tracked launcher before local ownership is established. Resolve the same first PATH candidate as today (including Windows npm layout), run a bounded --version check, and fail before spawning research if it differs. Do not silently skip an older first candidate to select an unreviewed later one. Error names required/observed version and resolved path; stdout remains clean MCP protocol. No global package installation or implicit npx download.

Doctor's explicit host probe confirms managed project scope and connections, then performs a bounded Rigup MCP initialize handshake through the same project launcher/PATH. Record responding serverInfo.version and compare to the expected version before declaring load passed. Plain doctor remains read-only and does not spawn research/model calls. Generated wiring continues to work after moving the project and from nested directories.

Remove the complete CodeGraph Windows idle override, parameter and generated branch; generic project entry resolution remains. Use upstream default on every platform, document roughly five-minute daemon linger and explicit stop/wait before moving the tool directory. Update tests/cleanup to stop fixture daemons explicitly. A v0.4.1 managed entry upgrades through ordinary B/L/N then no-ops; retain historical changelog evidence.

## E. Text ownership, fresh clones and filesystem modes (#50–#52)

Owned text equality normalizes CRLF to LF only for file/block text (JSON/TOML retain semantic parsing). Reuse equivalence in update, retirement, entry-block review and doctor. Genuine text/whitespace/permission edits stay protected. If both sides changed, normalize text for diff3 while preserving unchanged outside-block user bytes; do not normalize binary bytes. Full approved target digests and before/after modes remain exact for race detection, apply and recovery.

If no baseline exists and the selected local content equals the deterministic generated candidate under that ownership rule, the approved preview may record its ownership without rewriting local bytes. Establish generated baseline N, not local unrelated text, and preserve outside-selector content/mode. Equal bytes do not bypass incompatible explicit file modes. Differing unknown content remains conflict; report exact target, preserve/move-aside instructions and concrete re-review command. Do not add a general overwrite flag or silently adopt differing files.

Before any project content write, native install or durable prepared transaction, verify that each relevant filesystem can store the requested ordinary modes and private 0600 records. Probe each distinct nearest existing target parent (and metadata/tool roots), using an empty exclusive randomized temporary file and cleanup. Windows uses existing effective-mode and ACL policy, not POSIX equality. On unsupported mounts such as WSL drvfs without metadata, fail before project writes with observed/requested mode, path/mount where discoverable, Linux-home checkout or metadata guidance. No permissive acceptance of 0777 private state.

Existing interrupted preflight-missing installs keep journal and files untouched; report the same actionable mount guidance before mode comparisons. They can resume after the original project location gains proper mode support and permissions are reconciled; changed path/identity or old implementation requires existing explicit reconciliation. No blind journal deletion or automatic privilege change. Keep exact chmod/edit preservation on filesystems that do support modes.

## F. Windows GitLab probe and release verification (#49, all)

The disposable runner receives HOME and USERPROFILE. On Windows resolve a validated Git for Windows Bash installation (explicit test input or installed git executable/common install path), put bin/usr-bin before WSL bash and preserve essential Windows PATH; missing Git Bash fails with setup guidance. Use relative builds/cache paths under its explicit working directory. Capture failed job traces and runner failure evidence before deletion, redact API/runner/job token patterns and known values, and persist evidence even on test failure. Cleanup still removes disposable remote projects/runners and stops children.

Align handoff Node requirement with package engines (^22.19.0 || >=24.2.0); distinguish host Node from CodeGraph bundled runtime. Document WSL mount limitation and CodeGraph linger.

Testing seams are public lifecycle CLI/preview/apply/doctor; actual generated process launchers; provider HTTP + allowed repository reads; native host discovery/agent behavior; real installed npm/portable package. Tests use synthetic credentials/loopback targets, actual filesystem/git and bounded subprocesses. Avoid tests merely matching prose except template contract checks backed by native behavioral acceptance.

Verification covers macOS local and Linux/Windows in available local containers/Parallels or hosted CI. Matrix: supported Node 22.19 and current 24 on three OS for default check/audit/package; native Codex/OpenCode/oh-my-pi discovery, MCP and scoped workflow behavior on each supported OS; v0.4.1 update/unchanged review; CRLF checkout, WSL unsupported + metadata-supported mount where available; Windows runner probe; local MR fixture and actual host-driven read/fix/push/follow-up latest-SHA cases. Native agent probes must positively observe skill loading/prerequisite behavior and consume configured tools; fake drivers alone do not establish host behavior. Isolate homes/configs while reusing authorized existing authentication without printing or publishing it. Install missing dependencies when available, with bounded model budgets and per-attempt evidence. Unexpected pending/skip is an incomplete gate, not a pass. Claude real-agent execution alone is external by user request.

After all required gates, fresh implementation review and regression fixes, choose the next unused appropriate version (target 0.5.0 for new workflow/runtime features, verify releases first), update lock/changelog/guides, rerun version-sensitive checks. Push the repair branch, verify three-OS CI on its exact head, open/merge a reviewable PR with issue references after checks. Run four-target release dry-run on release commit; tag merged verified commit, follow release jobs through GitHub + npm publication. Compare release manifest and npm integrity, clean-install published version, portable smoke, then advance/install-check installer pointer through checked change. Report unresolved real platform failures; do not publish a knowingly failed required gate or mark goal complete before all requested outcomes have authoritative evidence.

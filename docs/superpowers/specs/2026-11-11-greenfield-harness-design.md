# Rigup 项目 Harness 统一初始化设计

2026-11-11 · 设计草案

`rigup init` 和 `rigup update` 共用一套规划方法。按仓库及模块识别可用的工程资产和约定，接入已有能力，为影响当前研发的缺口提供待填项。相同范围、输入和选项应得到相同的接入决策。

## Greenfield 与 brownfield

在 Rigup 的语境里，**greenfield** 指在给定范围内从头建设新的业务能力。已有服务骨架、团队模板、CI、共享组件和公司规范仍可复用。**Brownfield** 指接手并演进已有业务能力，需要考虑当前实现、对外契约、数据或运行约束。

范围可以是整个仓库，也可以是一个服务或模块。成熟 monorepo 里新建的服务可以是 greenfield。新仓库重写旧服务时，新实现可以从头建设，旧 API、数据迁移和兼容要求仍是这个范围的约束。仓库形态和业务约束可以分别说明。

这两个词用于描述工作背景。Rigup 的接入决策由**具体能力、适用范围和证据**决定。一个新服务可以已经具备 CI、部署、健康检查和安全约束，同时还需要填写业务验收。一个成熟服务也可以缺少浏览器测试或运行手册。 [Böckeler 对 greenfield 与 harnessability 的讨论](https://martinfowler.com/articles/harness-engineering.html)

## Harness 能力清单

这里的 Harness 指团队在项目中提供给 coding agent 的引导、执行条件、约束和反馈。清单用于发现候选能力。每一项只有在当前范围适用、且有实际消费者时，才进入初始化计划。客户自有工具或流程可以按同样的证据和接入条件纳入。

### 1. Agent 入口与项目知识

- **依据。** 宿主原生入口、README、架构或模块文档、代码索引和知识库。
- **已有。** 保留权威正文，在 Agent 入口或相关 skill 加简短导航。多个宿主共用正文。按实际索引范围接入 CodeGraph 或 OpenWiki。
- **缺失。** 选定宿主后生成最小入口。可先留项目目标、模块边界和知识来源的待填项。索引与系统现状由实际可读资料及索引结果支撑。 [OpenAI 的仓库知识导航](https://openai.com/index/harness-engineering/#we-made-repository-knowledge-the-system-of-record)

### 2. 工程与业务约定

- **依据。** 团队规范和客户已确认的约定、formatter/linter 和构建配置、可核实的代码与测试。可覆盖模块边界、代码风格、设计系统、API、鉴权、持久化、事件或领域不变量。
- **已有。** 引用原规范及适用范围。配置可证明它实际约束的行为。已有规范覆盖不足时，比较同类独立实现并检查反例，只有证据达标的模式才作为有范围的约定。单个脚手架示例可用于说明入口或局部实现。
- **缺失。** 对相关主题生成问题和空白的团队约定栏。例如已声明要提供 HTTP API，可以预留错误语义与兼容策略。团队确认后再作为规则引用。 [Rigup Analyzer 的规范复用与代码推断](scaffold-modules/01-project-analyzer.md)

### 3. 需求、实施、评审与交接

- **依据。** 原生 SDD、工单、PR 模板、现有 skills、评审责任和已明确的审批策略。
- **已有。** 接到所选 SDD 或项目流程，引用真实的规格、任务、验收及评审位置。 `change-prepare` 和 `change-deliver` 读取同一组适用约定与检查入口。
- **缺失。** 按用户选择和宿主支持准备基础流程。可预留规格位置、交接人和验收证据的填写项。具体任务、批准和结果随真实变更产生。 [Anthropic 的跨会话研发交接实践](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)

### 4. 开发环境、运行入口与测试数据

- **依据。** 依赖和锁文件、运行时配置、构建脚本、容器或开发环境配置、测试 fixtures、CI 中使用的命令。
- **已有。** 引用实际命令、工作目录、运行时和环境变量名。记录本地启动方式、服务依赖、隔离测试库或浏览器目标。只在真实环境执行后记录结果。
- **缺失。** 留启动、构建、准备和清理方式的填写项。客户选择有明确前置条件的团队模板时，可以渲染相应配置。测试数据、账号及凭据由真实环境提供。

### 5. 工具、MCP、skills 与原生 Agent 能力

- **依据。** 宿主配置、已有 MCP、skills、命令、子代理配置、客户 profile 或明确选择的集成。
- **已有。** 复用原生入口和项目配置，按任务与范围挂接。工具登记、连接校验和执行结果分别记录。
- **缺失。** 通过所选宿主支持的已核验适配器接入。工具用途明确但缺目标或凭据时，预留用途、目标环境和凭据变量名。没有使用场景的工具无需配置。 [Anthropic 的 Skill 加载机制](https://www.anthropic.com/research/equipping-agents-for-the-real-world-with-agent-skills)

### 6. 执行权限与操作边界

- **依据。** 宿主沙箱与工具权限、公司安全策略、分支保护、资源所有者、部署和环境授权。
- **已有。** 把已确认的环境边界、秘密引用和审批入口接到研发流程。由宿主及外部平台落实权限，报告可核实的状态。
- **缺失。** 对已计划接入的敏感操作预留目标环境、负责人和所需权限。实际启用仍取决于平台配置与授权。 [OpenAI 的 Codex 执行边界](https://openai.com/index/running-codex-safely/)

### 7. 质量检查与开发反馈

- **依据。** formatter、lint、typecheck、build、测试脚本和断言、架构与安全检查、浏览器场景、API 契约测试、测试报告。
- **已有。** 绑定真实命令或报告入口，明确检查覆盖范围、前置服务和反馈时机。骨架的构建和健康端点可以当天验证。相应结果只覆盖这两项。
- **缺失。** 先记录拟验证的场景、通过条件和反馈位置。可以先指定人工评审项。有可运行入口、环境及断言后再接自动检查。 [Böckeler 的 Guides 与 Sensors](https://martinfowler.com/articles/harness-engineering.html#FeedforwardAndFeedback) · [Thoughtworks 的反馈检查实践](https://www.thoughtworks.com/en-sg/insights/blog/generative-ai/harness-engineering-agent-feedback-exploring-ai-coding-sensors)

### 8. Hooks、CI、发布与恢复

- **依据。** 已启用的 hooks、CI 作业和触发条件、共享模板、runner、发布目标、审批记录与回滚手册。
- **已有。** 复用项目命令和对应作业，保留流水线定义及项目所有权。远端 include 不可读时，记录可见引用和待核实的覆盖。发布结果以实际平台和环境为准。
- **缺失。** 对有交付需求的项目，预留要运行的检查、触发时机、目标环境、冒烟和回滚入口。所选适配器具备真实命令、runner 和环境条件后，可通过预览补接作业。 [Claude 的 SDLC 交付实践](https://claude.com/resources/articles/the-ai-native-sdlc-playbook)

### 9. 运行反馈与 Agent 操作记录

- **依据。** 健康端点、测试环境日志和追踪、监控面板、告警、事故手册，以及宿主的 Agent 工具调用与操作审计。
- **已有。** 把可访问的信号接到调试、验收或交付。分别记录应用运行证据和 Agent 执行记录的来源、环境及访问范围。
- **缺失。** 针对已存在或明确计划的运行场景留信号入口和负责人。运行环境和实际数据可用后，再配置探针、诊断或告警。 [OpenAI 的浏览器与遥测反馈](https://openai.com/index/harness-engineering/#increasing-application-legibility)

### 10. Agent 与 Harness 评估

- **依据。** 可复现的任务、预期产物、工作流触发记录、历史失败样例、评分条件和实际结果。
- **已有。** 引用团队 eval 命令和样例，记录环境、评估对象和结果。产品测试验证应用行为，Harness eval 可检验 Agent 是否读取适用规则、调用工具并交付预期产物。
- **缺失。** 先保留值得重复检验的任务及成功条件。等输入、环境和验收方式具备后接入评估。Rigup 自身可先验证链接、配置和重复应用。 [OpenAI 的 Skill 评估实践](https://developers.openai.com/blog/eval-skills) · [Anthropic 的 Agent Evals](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

## 按模块动态识别

Analyzer 读取用户选择和团队 profile，以及仓库内可读的文档、配置、代码、测试和流水线。在现有项目画像中记录**能力或主题、适用范围、来源、覆盖状态、使用者和待补项**。识别基于具体入口和行为，也接受明确标注的用户计划。框架依赖或目录名可以提供搜索线索，确认接线仍需要对应入口或配置。

- 发现浏览器页面或团队明确声明 UI 后，才检查设计系统、交互状态、可访问性和浏览器验收是否需要接入。
- 发现业务 HTTP 路由、API 规格或对外接口计划后，才检查输入校验、错误结构、鉴权和兼容性。事件消费者按事件契约、重试与幂等检查。数据库或迁移证据会引出事务、迁移和隔离测试库。
- 同一仓库可以有 UI、HTTP、批任务、消息消费者、库或 CLI。根据各自入口组合主题。前后端共享 API 契约时引用同一来源，分别记录消费目录和验证入口。
- 只看到依赖清单或基础文件时，先完成通用接线。已有团队 profile 可以补充计划能力和明确选择，声明的计划保持「待实现」或「待验证」。识别结果随证据变化，不需要必填的 `projectType`。

## 按证据做接入决策

1. **已有且足够。** 按范围引用原文、命令、作业或适配器。项目文档说明团队约定，实际配置说明当前强制行为，运行记录证明某一次执行结果。分别用对应证据支持结论。
2. **已有但部分覆盖。** 先复用已知部分。仅为影响当前研发的缺口研究代码、接入已有检查或生成待填项。例如已有健康检查时，可以复用启动探针，同时给业务场景留空。
3. **依据缺失。** 适用性已明确且团队已选可信模板时，用模板提供可确定的接线。需要团队决定时，给出具体待填问题和验收位置，内容可以为空。只有线索的能力在报告中标记待识别，已有适用范围的待填项才进入文档。
4. **来源冲突或不可核实。** 保留各自范围与出处。政策与实现冲突时报告差异，远端来源不可读或扫描未覆盖时标记待核实。待决的内容留给相关提案或负责人处理，已核实的其他能力可继续接入。

现有规则分析已经区分可复用、部分覆盖、缺失、冲突和不可读，可以扩展到检查、工具与流程。初次接入和后续更新沿用 **Analyzer → Generator → Installer**。Analyzer 发现证据和缺口，Generator 组合引用、已选 recipe 和待填文档，Installer 通过现有预览与应用机制写入。确定性读取与模板渲染支持零模型调用，有必要时才研究规则缺口。可执行能力的必需前置条件缺失时保持待接入，团队仍可应用独立的基础接线。 [Analyzer](scaffold-modules/01-project-analyzer.md) · [Generator](scaffold-modules/02-rigup-generator.md) · [Installer](scaffold-modules/03-rigup-installer.md)

### 同一主题在不同仓库中的处理

以 API 错误处理为例。新服务的骨架只有健康端点和 build 作业时，Rigup 引用现有启动和 CI 入口。团队已计划提供业务 API 时，才为错误语义与验收生成待填项。已有 OpenAPI 或团队错误规范的服务直接引用原文，并关联可用的契约检查。只有零散实现的服务先核实适用范围，发现多种做法时列出差异和待决问题。新仓重写旧服务时也可引用旧契约及迁移要求。

首版按主题和适用范围创建客户维护的约定页，默认放在 `docs/rigup/conventions/`。文件名由 topicId 与规范化 scope 的摘要组成，使用扁平目录避免文件范围与目录范围碰撞；导航显示可读的标题和范围。页面用 YAML 元数据记录主题、范围、待决定的问题、验证方式、结果位置及「待填写」「已确认」「不适用」状态，Markdown 正文留给团队填写。每个主题/范围身份仅首次创建，经确认的正文才作为团队约定。新增缺口可创建新页，更新保留客户已经填写的内容；修改文档目录不重置创建历史。已有权威文档足以覆盖时直接引用原文。具体契约见[首版实施计划](../plans/2026-11-11-unified-harness-v1-implementation.md)。

## 安装、更新与验收

- **所有权。** Rigup 管理自己的导航和接线。客户维护原文与填写后的约定。更新按实际目录和证据复核，缺口补齐后可更新引用，已有内容通过预览和现有合并保护保留。
- **状态。** 预览展示已发现的来源、将接入的能力和待填项。诊断分别报告配置状态、工具连接状态与最近的实际检查结果。规则研究完成但没有可引用正文时，显示「暂无适用规则」。
- **同一主线验收。** 分别用纯空仓、已有骨架和 CI 的新服务、已有规则和实现的成熟服务，以及成熟仓库含新模块的混合项目验证同一流程。检查已有来源可达、已有 CI 作业复用、缺口按范围生成，预算受限或远端来源不可读时能正确报告。
- **动态识别验收。** 用可运行页面、HTTP 服务、事件消费者和共享契约的项目样例核对主题选择。新增代码或模块后再次执行 `update`，应能补充新证据、保留客户正文，并验证相同输入重复应用时不会重复写入。

# Project Analyzer：项目分析

所属：[总架构](../2026-11-02-rigup-design.md)。

## 1. 职责与接口

```typescript
analyze(root, options, backend): Promise<StepResult<ProjectProfile>>
```

输入是项目位置、用户选择、读取范围和预算。输出是技术栈、模块、已有配置/检查入口、规范事实、来源、未知项和输入指纹。本模块只读客户项目。语义研究先识别并复用项目已有规范，针对缺口再从代码中识别可复用的实现模式、核实其适用范围并提炼开发约定；不生成系统 AS-IS，后者全部由 OpenWiki 负责。模块/调用关系只作为判断模式所需的内部证据。

同时发现已有启动/环境检查、开发容器和环境变量引用、软件测试与 Agent eval 入口，以及知识维护者/失败接手人的现有记录。能读到配置不等于运行成功；无来源时标未知，不猜测身份、权限或负责人，不运行初始化脚本。

扫描与语义研究作为一个模块的两个内部步骤，不需要 CLI 在两者之间管理额外状态对象。

## 2. 流程沿用 OpenWiki 的研究与生成方式

以[已有源码研究](../../../research/2026-11-02-openwiki-analysis-generation.md)为实现参考：先研究输入并提出产物计划，程序校验并保存计划，再围绕每个产物补充研究、生成候选、校验接受，最后汇总并支持恢复。Rigup 不另建一套模式挖掘调度流程。

差异集中在研究问题和产物：OpenWiki 研究系统如何工作并生成 AS-IS；Rigup 研究已有规范如何复用、代码中哪些做法可提炼为开发约定，并产出原文接入引用、补缺规范和项目专属 skill references。AS-IS 的生成继续由 OpenWiki 自己负责。

Analyzer 是规划前的初步研究：发现已有规范、可复用部分和待调查主题，取得足以规划的证据即可。Generator 规划后的每项研究再核实该主题的支持、反例和范围，复用已得到的证据，不重新完整调查仓库。2.0/2.1 是 planner 与逐项研究共同使用的问题和质量要求，不是额外必经阶段或单独分析平台。未完成的主题保留未知/待核实，不能把初步画像当成已完成所有规范研究。

初步研究、产物规划和逐项生成共用现有 AnalysisBackend、reader、预算及缓存。参考其流程与职责划分，不要求调用 OpenWiki 的内部 API、复制其 Claims/并发运行时，也不让未选用 OpenWiki 的规范研究依赖其软件安装。

### 内部步骤

1. 定位真实目录、Git/worktree 和当前 HEAD；无 Git 或空仓库是明确状态，不提前创建。
2. 枚举相关文件，读取构建 manifest、agent/CI 配置和既有文档，跳过依赖缓存、二进制和生成区。
3. 提取已有构建、lint、测试命令，只记录入口，不执行任意项目脚本。
4. 先按 2.0 识别现有规范、适用范围和开发消费者；可直接复用的仅建立接入关系。缺少或不足的主题再按 2.1 分组调查实现模式；已有规范仅做与接入有关的必要核对，不重复完整反推。
5. 将显式规范、常见惯例、局部模式和改进建议分开，保留支持/反对证据、适用范围、例外和未知项。
6. 保存 ProjectProfile，作为生成器的输入。

初步研究在足以判断复用/缺口并规划产物时停止；逐项研究在约定候选的支持证据、反例搜索和适用边界已完成时停止，二者都受同次预算限制；不是写完系统概览或扫描每个文件。预算停止时记录未完成的验证，不将未观察到当成不存在。

## 2.0 先复用已有规范，再研究缺口

先检查 README/CONTRIBUTING、docs 中的开发约定、根与模块级 agent 入口、现有 rules/skills、lint/类型配置及用户明确指定的规范来源。按内容和声明范围识别，不能只按文件名或“有 docs 目录”认定已满足。AS-IS 页面不是开发规范的自动替代品。

对实际开发需要的主题分别判断：

- **足够且可定位：** 保留原文和原路径，记录引用、适用范围及使用步骤；不为换成 Rigup 格式而重新总结一份，也不要求规范先得到多数代码支持才能采用。
- **部分满足：** 复用已有部分，只调查缺少的情形/范围/范例。补充内容指回原规范，不能悄悄改变其语义或扩大适用范围。
- **缺失：** 进入 2.1 的代码调查，再按证据决定是否产出惯例/参考。
- **冲突或无法核实：** 保留来源和差异，标 needs-decision/unknown。文档与实现不一致不自动认定文档过时；不同文档也不按修改时间或模型偏好选赢家。用户已有明确裁决、文件声明的作用域/替代关系可以采用，并保留依据。

内部在 ProjectProfile 的已有知识入口/规范信息中记录 `sourceRef`（路径及章节/行号，远端为明确引用）、`scope`、`coverageStatus`（reusable/partial/missing/conflicting/unavailable）、`consumers`（开发/实现/评审步骤）、`gaps`。复用原文时，代码支持/反例覆盖可标 not-researched，不编造“已验证与实现一致”；代码模式的证据门槛只用于代码推断项。

本地可读文档沿用 reader 脱敏与证据策略；远端材料只在已有可用适配/权限范围读取，无法读取则保留引用与 unavailable，不假装已理解内容。存在不可访问引用不自动触发远端抓取或新的凭据流程；按所选必需能力决定是报告缺口还是阻止依赖操作。

复用的完成条件包括内容可用与接入可用：Generator 要将原来源接到实际 agent/skill/检查使用点，不能只在安装报告中列出文件名。既有规范继续由项目维护，Rigup 只拥有自己增加的导航/接线块；发现文件不构成接管或改写授权。

## 2.1 从代码识别模式并提炼约定

这是现有规范不足时的核心补缺能力，不替代 2.0 的优先复用。目录、依赖和命令的静态发现只是研究入口，不足以证明项目采用某种设计模式或规范。现状总结不作为本模块的交付目标。

### 研究什么

关注会影响下一次改动的重复做法：新增接口/用例如何分层和接线、模块依赖边界、参数与配置传递、校验/鉴权位置、错误转换与返回结构、事务边界、异步/资源释放、日志与可观测性、依赖注入、命名及同类测试的组织方式。按项目实际存在的结构选择研究主题，不套一份“最佳实践”清单，不推断未经确认的业务规则。

### 研究步骤

1. **划定可比较范围。** 按模块、语言、生产/测试代码及接口/服务/存储等实际角色分组；识别生成代码、vendor、样板复制和迁移/遗留区。排除项及理由留证，不从某个目录名就断定其过时。现有规范、formatter/linter/类型约束优先作为显式依据，配置未验证执行时不宣称已强制生效。
2. **提出模式假设。** 从真实调用点和实现对照提出具体说法，例如“订单模块的 HTTP handler 将已知业务错误交给统一转换函数”；不能只有“遵循分层架构”这类标签。记录研究入口，继续追踪到足以判断行为的位置，不能只看函数名/import 或相似文本。
3. **找独立支持和反例。** 在同角色代码中搜索其他用例，并专门寻找绕过/不同实现。生成副本、同一模板的机械复制不充当多个独立支持；相似文本只是线索。以可比实现位置为分母而非仓库总文件数；只枚举了样本就记录样本数和覆盖范围，不编造全仓采用率。
4. **解释差异并收窄范围。** 差异可能来自不同职责、明确例外、并存实现、迁移或缺陷；只能在有证据时说明原因，不能自动称少数实现为违规/遗留。无法解释时保留 competing patterns 或降为局部观察。跨模块结论必须实际检查所声称覆盖的模块；未研究模块不继承结论。
5. **确定可用结论。** 按下述分类与证据规则输出；证据不足可以不产出某条约定。模型偏好的做法只能进入建议，不混入已识别的项目惯例，更不能自动成为阻断规则。

### 最小证据与分类

- **显式规范：** 有可定位的项目规则、配置或客户确认依据，保留其声明范围。代码与其冲突时记录差异；这不使显式规则失效，也不让当前实现自动变成新规范。
- **常见惯例：** 至少两个独立同角色实现支持，且完成一次针对该假设的反例搜索，才允许作为候选。这个下限只避免从单样例概括，不代表统计充分；仍须按样本覆盖和差异收窄为“已观察范围内的惯例”，不声称团队规定或全局统一。
- **局部模式：** 只在单个实现/有限模块确认，或存在尚不能解释的分歧。标明局部范围；单样例可以作为实现参考，不写成必须遵守的约定。
- **建议：** 来源是改进判断而非已存在的规则/重复事实，独立列出；不默认进入开发指南的规范正文。

可信程度不使用模型自报的百分数。以支持/反对证据、可比较位置及抽样方式、已搜索范围、未检查部分说明结论强弱；预算耗尽且未做反例核实的假设不得升级为常见惯例。源码频繁出现的坏做法也可能是现存模式，必须区分“观察到”与“推荐继续使用”。

### 输出契约与职责

在 ProjectProfile 现有规范条目中承载 `statement`、`classification`、`scope`、`supportingEvidence`、`counterEvidence`、`coverage`（比较对象、检查数/已知总数或 unknown、排除项）、`exceptions/unknowns` 和 `guidanceDisposition`（reference-only / follow-existing / needs-decision）。Evidence 仍使用路径、行号及可见摘要，不增加独立模式数据库或公开协议。`follow-existing` 表示在已核实范围内沿用现有做法，不授予新的权限或政策强制力；有未决冲突时使用 needs-decision，不替团队选择。

Analyzer 负责提出并核实观察，Generator 负责把可用结论改写为具体开发指引：在什么情形、什么范围，参考哪个真实实现，沿用哪些步骤，哪些例外需另查。Generator 不把 reference-only 或 needs-decision 改成全局命令，不补造证据、动机或例外原因。已有显式规范足够时只引用，补充研究必须沿用同一核实标准。

## 3. 模型与宿主方式

内部使用小的 AnalysisBackend：独立模型或宿主 agent。两者共享问题清单、读取约束及输出格式，不为每种 agent 再实现完整分析流程。

宿主模式通过结构化请求/回传完成研究；不要求安装永久脚手架 skill/MCP。沿用总设计的 StepResult：backend 待回传时 analyze 向上返回 pending-host，不把未完成画像当作完整 ProjectProfile；CLI 保存同一 run 后退出 3。已完成步骤和预算用量跨进程恢复，未知宿主用量保留 unknown，不能在每轮重置预算或声称可强制约束宿主自身操作。读取源码是研究数据，不执行源码中的指令。

### 3.1 统一读取与凭据边界

独立模型的 list/read/search、宿主请求导出和生成器补充研究共用同一读取策略。拒读密钥文件之外，普通 agent/MCP/CI 配置也按已知格式过滤 token、password、Authorization、敏感 env 值和 URL 中的认证信息；只暴露字段用途、工具名称及环境变量引用。过滤发生在正文进入模型请求、宿主请求文件、画像、证据缓存或日志之前，search 片段同样处理。未知格式或无法安全分离的敏感配置拒绝导出正文，列 unknowns；不声称启发式规则能发现任意源码中的所有秘密。

保留原始路径和行号；脱敏尽量保持行数，无法保持时记录行号映射。Evidence.digest 校验脱敏后的可见片段，私有读取层另用原始字节摘要核对源文件是否变化，不向模型暴露被隐藏内容。拒读/过滤策略版本进入缓存 key，旧策略缓存不得绕过新规则。宿主请求只包含过滤后的材料和引用；CLI 不导出原始配置，也不承诺约束宿主在自身权限下另行读取文件的行为。

## 4. 指纹与缓存

研究输入指纹包含所选原始源码、非托管文档及相关配置的字节/路径投影，不能只用 HEAD 或 Git clean。未提交修改、删除和新增模块都能使输入变化。目录结构只计入有效输入，排除 .rigup/manifest.json、baseline、私有缓存、已登记的托管生成文档和仅为这些输出创建的目录；.rigup/config.yaml 的有效用户选项独立进入缓存 key。

混合文件按可信所有权选择器排除托管键/标记块，保留非托管内容作为研究输入；不能直接忽略整份 agent 配置。托管生成正文不作为独立项目规范证据，即使被用户修改也不自动升级为权威来源；用户可将规范明确维护在非托管来源中。无法可靠解析所有权时列未知项并停止相关缓存复用，不把疑似输出当作新规范。

研究输入指纹与安装目标前置摘要用途不同：后者始终检查完整目标的实际字节，包括托管部分的用户修改和删除。排除研究输入不影响三方合并、删除保护或陈旧预览检查。Analyzer 使用只读所有权元数据/纯投影函数，不调用 Installer 执行逻辑；相关纯函数先在 Task 2 建立，Task 6 复用。

同输入、选项和模型/prompt 版本可复用缓存。缓存丢失就重新分析；浅克隆无法使用旧提交时读取实际文件，不猜测没有变化。

集成 recipe 明确其 SDD/OpenWiki/CodeGraph 生成区及纯投影规则；只有已核验的生成输出才排除，目录中混有用户输入时保留该部分。工具版本或用户源码/配置仍使缓存失效。已有远端适配读取的规范在复用缓存前核对明确版本或内容摘要；版本未知则本次重读，无法重读时记 unavailable，依赖其内容的旧语义结果不可复用。仅作为不可读导航的 URL 不被当作已理解规范；此检查不新增抓取器或凭据流程。

首版不追求逐事实精确失效：重要输入变更可重新研究整个所选范围。读取失败或预算耗尽返回部分结果与未知项，不假装分析完整。

## 5. 边界与测试

不修改配置、生成业务测试或决定团队政策。模型建议不自动变成阻断规则。

用隔离项目验证：空项目、无 Git、worktree、monorepo、隐藏配置、未提交变化、预算截断和无法读取文件。模型结果验证来源和分类，不要求正文逐字相同。模式识别另覆盖：生产/测试与跨模块不同模式、机械副本不算独立证据、单样例不概括、主动发现反例、显式规则与多数实现冲突、无法解释的并存模式、预算未完成核实、建议不冒充惯例。固定 fixture 标注预期分类/范围/支持与反例，不只验 JSON 结构；真实模型和宿主分别检查是否找对事实与边界。另验普通配置内嵌凭据和 search 片段的过滤、脱敏后行号/摘要可核实、未知敏感格式拒读、托管输出不改变研究输入、非托管配置/源码变化仍失效，以及托管项用户删改仍被目标摘要检测。

# Rigup 设计修改意见汇总与整体复核交接

日期：2026-11-03。用途：汇总本轮用户明确的方向与已落文档的方案，供新会话独立整体 review。产品尚未实现；文档链接/结构检查通过不代表真实模型效果或兼容性验收通过。

## 1. 用户确认的修改方向

1. **范围是整个脚手架。** 明确固定部分、需要理解的部分和用户决定，不能把所有配置、脚本或流程都交给 agent 生成。
2. **确定性骨架加有边界的语义研究。** CLI、已知格式扫描、集成 recipes、机器配置、脚本、skills 主流程、安装更新/恢复与真实检查结果由代码/模板负责。固定结构可以参数化。
3. **核心难点是规范理解与模式提炼。** 从真实代码比较同类实现，寻找独立支持及反例，判断适用范围；区分显式规范、惯例、局部模式与建议，不能把现存多数做法直接升级成全局政策。
4. **先复用已有文档。** 已有规范足够则保留原文/路径，只接入；部分满足则只调查缺口；没有时才调查总结。文档与代码冲突不自动改写文档。
5. **复用要整合进 harness。** agent 入口按任务指向规则；prepare 读取规则形成方案约束；deliver 在实现/评审中使用同一来源；已有检查按选择接 hooks/CI。只存在文字规则时不声称自动强制。
6. **AS-IS 全部归 OpenWiki。** Rigup 不生成 context.md、架构百科、模块现状页，也不因 OpenWiki 不可用而自建备用现状生成器。只保留必要接线和引用。
7. **流程参考 OpenWiki。** 初步研究 → 动态产物规划 → 逐项深入研究/生成 → 校验接受 → 汇总/恢复。区别在研究重点和产出；不另建模式分析平台。
8. **文档服务开发。** 收缩为项目开发指南、skills 流程指引、原生变更工作文档三类用途；setup 只生成前两类必要部分并配置原生落点。术语、ADR、交付/事故记录等不作为默认文档全集。
9. **开工前收口三件事。** CLI 细则落实测试，上游版本/命令/写入证据明确规则，实施完成与真实生成/兼容/完整验收分别判断。

## 2. 当前方案如何落地

- [总设计](../superpowers/specs/2026-11-02-rigup-design.md)：1.1 节定义全项目的确定性/agent/用户/外部工具边界，四模块架构保持不变。
- [Analyzer](../superpowers/specs/scaffold-modules/01-project-analyzer.md)：初步研究足以规划即可；2.0 先发现现有规范、范围和缺口；2.1 对缺口比较代码、搜索反例、形成带范围的观察。逐项任务继续补证，不先穷尽全仓。
- [Generator](../superpowers/specs/scaffold-modules/02-rigup-generator.md)：固定机器资产/流程由模板渲染，语义任务沿 OpenWiki 方式串行生成私有候选并校验接受。复用原文接入，补缺正文保留范围/范例/例外。
- [Installer](../superpowers/specs/scaffold-modules/03-rigup-installer.md)：所有权、三方更新、差异预览、锁、取消、对账、恢复与最终落盘由确定性代码承担。
- [Integrations](../superpowers/specs/scaffold-modules/04-integrations.md)：版本化 recipes 与真实原生绑定，不能由模型临时发明可执行 adapter。
- [开发文档标准](../superpowers/specs/2026-11-03-documentation-system-design.md)：三类用途及具体生成标准；第 4 节明确已有规范接到 agent/prepare/deliver/评审/检查的方式。
- [安装后的 skills](../superpowers/specs/2026-11-02-installed-skills-design.md)：prepare/deliver/release 复用原生 SDD，与 setup/update 生命周期分离。
- [CLI 交互](../superpowers/specs/2026-11-03-cli-interaction-design.md)：先集中决策再连续执行，可选生成后审阅；宿主往返绑定上下文、取消需确认写进程退出等。
- [实施计划](../superpowers/plans/2026-11-02-rigup-implementation.md)：保留九任务主线，补复用/模式识别/接入、固定流程保护、无模型路径及真实验收行为测试。
- [上游核验](../compatibility/README.md)与[验收状态](../compatibility/verification.md)：只定义证据规则，真实版本、执行与生成效果仍待实施核验，目前 pending。

## 3. 实现细节属于当前方案，仍需审阅

以下是本会话提出的实现取舍，不等于用户逐项确认过的要求：规范条目的字段及状态枚举；“两个独立样例加反例搜索”只作为常见惯例候选的最低门槛；ArtifactJob 字段；可纯确定性执行的条件；缓存/版本绑定与具体测试名。新 review 应判断必要性、一致性及是否过度设计，可提出更简单的替代。

不需要重新讨论已明确的产品方向；如发现这些方向在实现中互相制约，应指出具体冲突及最小解决方案，不擅自缩减四宿主/三 SDD 等原需求。

## 4. 新会话整体 review 的要求

请从[需求基线](../requirements/2026-11-02-rigup-requirements.md)出发，阅读上述完整设计、四模块、CLI、skills、文档标准、实施计划和证据规范。汇总只是导航，不能替代独立检查。

重点审阅：

- 全项目确定性与语义边界是否一致；固定流程是否可能被模型正文改写；已有文档的存在是否被误当成已完成理解。
- 初步研究/逐项研究、profile/plan/job/preview/apply 接口与任务顺序是否衔接，是否重复研究、规则过多或在开工前还缺关键决策。
- 规范复用、部分补缺、从零调查三条路径是否具体可实现；引用能否实际进入 agent/skills/检查；现有资产与用户修改是否受保护。
- 模式识别证据、反例、范围、不确定性及真实验收是否足够，是否出现模型自评循环或无依据的支持承诺。
- OpenWiki 参考机制与实际软件依赖是否混淆；AS-IS 是否又从其他地方被纳入 Rigup 生成。
- CLI 前置授权、连续执行、host 多轮、缓存失效、输入变化、退出码、取消/锁/远端结果未知等是否一致。
- 九任务计划是否能完成需求、测试是否证明真实行为，mock/静态检查与实际模型/宿主验收是否分清。

先做只读 review，不开始产品实现、不安装依赖、不批量重写方案、不提交/推送。按严重程度列出可行动发现，给出精确文件/行号、影响和最小修订建议；区分开工阻碍、实施期核验及非阻碍建议。即使无发现，也写明检查范围与尚未验证部分。

将整体 review 写到 docs/reviews/2026-11-03-overall-design-review.md，最终回答是否可以开工、开工前必须收口什么。文档仍有未提交/未跟踪和既有重命名改动，应读当前工作目录的真实文件，不只看 Git HEAD/diff；不要撤销、暂存或提交用户资产。

## 6. 整体评审后的修订（2026-11-03）

用户随后要求修复[整体评审](2026-11-03-overall-design-review.md)发现的问题。本次仍只修订文档，不执行原实施计划。

- 外部命令的声明路径不再被视为覆盖授权；项目文本先成为候选，原生状态按已核验保护方式执行，目标重叠不能直接写。
- Generator 接收旧 manifest 的只读库存，每项交代去向；保留项保存 ownership/可信旧 B，已知失效且仍可加载的规则阻止完成，省略不授权删除。
- backend/analyze/generate 共用 StepResult；pending-host 保存同一 run 的节点、已接受候选、预算累计和授权关联，退出 3，不产生可安装的部分计划。
- 客户扩展明确支持本地标量文本模板及结构化 MCP 输入；有真实消费者、源摘要及三方保护，固定流程/gates 不可替换。
- 实施计划补齐真实工具输出/远端规范的缓存核验、项目检查红仍保存成功接线、host 先响应再停会话/apply、整轮执行锁及独立于普通缓存的未决操作记录、矛盾正文与真实 gate 行为验收。
- 进度先实现准确计数、等待、已用时间和下一步；无可比依据时待估算，移除固定初始权重/样本数作为产品约束。

上述是本次设计修订取舍；未缩减四宿主/三 SDD 或 AS-IS 归 OpenWiki 的方向。版本、真实运行、生成效果及首版完整验收仍 pending，当前开工判断以整体评审中的修订复核为准。

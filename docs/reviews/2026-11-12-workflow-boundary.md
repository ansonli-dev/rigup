# Workflow bypass acceptance correction

The authoritative #45 comment requests a bypass-wording acceptance run with no approved change, and an accurate explanation of what is enforced when the skill is not loaded. It describes the existing gate as dependent on the agent following the skill and the host controlling writes. It does not require Rigup to override the host's instruction hierarchy.

Three Codex 0.166.0 attempts on macOS used changing template and prompt snapshots; the first two prompts were identical. The first and final attempts observed generated skill/reference reads and native prerequisite inspection. The retry did not affirmatively observe native status/instructions and exceeded its token budget, so it remains incomplete evidence. The final attempt removed both approval and design and still edited source after loading the skill and reading native prerequisites. Its observable response explicitly stated that the user's instruction overrides the skill requirements. Original failure records remain unchanged under the private per-attempt evidence directories. The final attempt establishes an observed boundary even after loading, broader than the previously documented no-load case.

The original implementation test asserted refusal for every loaded bypass. That assertion overstates the issue's requirement and the advisory implementation's capabilities. Do not rename these attempts to successful refusal or discard them.

Proposed corrected acceptance:

- Preparation and ordinary readiness/delivery must positively demonstrate skill/GOAL and native status inspection, identify the actual missing prerequisite or approval, keep same-change references and withhold readiness when blocked. Compare independent before/after source/test content and local HEAD as well as uncommitted status and remote head; a clean local commit cannot masquerade as a read-only run.
- An explicit bypass pressure case must actually execute through each tested native host, record whether the skill and native state were read, and independently record whether source or test files changed. It is a capability characterization, with `refused`, `host-override` or `unverified` as distinct outcomes. Unverified execution remains incomplete.
- Publish observed host-override outcomes and state that loading a skill is not an access-control boundary. Do not claim that skills can prevent writes, even if a particular prompt is refused. Stronger restrictions must come from the host's permissions/sandbox.
- Positive implementation/MR gates remain behavioral pass/fail: actual scoped fix, required checks, every outgoing push reviewed, configured CI/review completed and findings disposed for the current head SHA. Capture the agent's event log before independent oracle API reads, and require agent-originated current-head checks/review/discussion reads after the last push. Missing-prerequisite and missing-approval ordinary readiness/delivery scenarios remain read-only pass/fail.
- The existing literal `/goal` prompt sent to `codex exec` demonstrates a GOAL-guided implementation, not native slash-command dispatch or persistent goal state. A bounded real native `/goal` dispatch remains required and must be recorded separately.

This correction changes an overstrong test interpretation, not the user's issue scope, and adds no workflow executor or blanket write restriction. Independent review against the complete design, execution plan, issue text and actual harness is required before adopting it.
